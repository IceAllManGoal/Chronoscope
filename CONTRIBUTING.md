# Contributing

Спасибо за интерес к Chronoscope. Ниже — правила, которые помогают держать проект консистентным.

## Лицензия вклада

Проект распространяется под [MIT](LICENSE), см. [ADR-0009](docs/decisions/0009-mit-license.md). **CLA не требуется** — отправляя pull request, ты соглашаешься, что твой вклад распространяется под той же лицензией.

## Прежде чем писать код

Прочитай, в зависимости от задачи:

| Документ | Когда нужен |
|---|---|
| [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md) | Всегда. Это главный документ проекта |
| [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) | Всё, что касается структуры и слоёв |
| [`docs/EVENT_MODEL.md`](docs/EVENT_MODEL.md) | Всё, что касается событий, схем и идентификаторов |
| [`docs/decisions/`](docs/decisions/) | Прежде чем предлагать архитектурное изменение |

## Границы 0.0.1

Список того, что **не** входит в текущую версию, находится в §74 спеки: Sysmon, ETW, сеть, DNS, файлы, реестр, службы, драйверы, performance, GPU, Steam, 1С, UI, correlation, anomaly detection, compare mode, plugin SDK, installer, auto-update, AI.

Если во время работы хочется добавить что-то из этого списка — запиши в backlog и продолжи 0.0.1.

## Архитектурные решения

Существенные решения фиксируются ADR в `docs/decisions/` по шаблону [`template.md`](docs/decisions/template.md).

ADR обязателен, если изменение затрагивает:

- архитектурные инварианты (§81 спеки);
- контракт между Agent и Core, включая JSON-схемы;
- схему БД;
- формат идентификаторов;
- модель времени;
- модель приватности;
- зависимости (см. §65 — «не добавлять dependency только ради небольшого удобства»).

Для мелких изменений ADR не нужен.

## Definition of Done

Изменение считается завершённым, когда (§71):

- код работает;
- есть адекватная обработка ошибок;
- есть тесты нужного уровня;
- обновлена документация;
- нет очевидного privacy regression;
- есть способ проверить функцию вручную;
- создана миграция, если изменилась БД;
- рассмотрена версия schema/API, если менялся контракт.

## Приватность

Chronoscope видит потенциально чувствительные данные: командные строки могут содержать токены, пароли, ключи и приватные пути. Изменение, которое расширяет собираемые данные или ухудшает redaction, требует отдельного обсуждения и обновления ADR-0009-соседних документов: спеки §37–§38 и [`SECURITY.md`](SECURITY.md).

## Стиль кода

- Основа — [`.editorconfig`](.editorconfig): UTF-8, LF, финальный перевод строки, 4 пробела (2 — для JSON/YAML/TOML/MSBuild).
- Ясность важнее clever-абстракций (§70).
- Не строить framework заранее: если коллектор один, не нужно 20 уровней plugin-инфраструктуры.
- Core следует правилам слоёв (§50): `domain/` не зависит от FastAPI, SQLAlchemy, SQLite, HTTP и Windows; API не пишет SQL самостоятельно.

## Тесты

Стратегия описана в §58 спеки. Уровни:

```text
unit         — normalizers, value objects, валидация, генерация ID, domain rules
contract     — совместимость Agent ↔ Core и общих JSON-схем
repository   — временная SQLite: insert, дубликаты, queries, ordering, миграции
integration  — POST raw event → raw stored → normalized → GET event
e2e          — процесс целиком (см. §75)
```

Фикстуры для тестов берутся из `shared/fixtures/` — так normalizer тестируется без запуска реальных процессов.

Эти уровни прогоняются в CI на каждый pull request. Правила слоёв §50 проверяются механически, а не только на ревью: `core/tests/test_layer_rules.py` следит, чтобы `domain/` и `normalization/` не импортировали FastAPI, SQLAlchemy, SQLite, HTTP и Windows API.

Тесты Agent прогоняются отдельно:

```powershell
cd agent
dotnet test Chronoscope.Agent.sln
```

Общей для обоих компонентов остаётся не только документация, но и контракт: `shared/schemas/` — тот файл, против которого обязаны сходиться и сериализация Agent, и валидация Core. Изменение схемы без изменения обеих сторон обнаружится именно там.

## Коммиты и pull requests

- Ветка от `main`, осмысленное имя: `feat/ingest-endpoint`, `fix/duplicate-raw-event`.
- Коммит описывает, **что** изменено и **зачем**; для архитектурных изменений — ссылка на ADR.
- В PR: что сделано, как проверить вручную, какие тесты добавлены.
- Не смешивать в одном PR несвязанные изменения.

## Сообщения об ошибках

Обычные баги — через GitHub Issues. Уязвимости — не в публичный Issue, а по процедуре из [`SECURITY.md`](SECURITY.md).
