# Changelog

Все заметные изменения Chronoscope документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версионирование — [Semantic Versioning](https://semver.org/lang/ru/). Правила версионирования до `1.0.0` описаны в §72 [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md).

## [Unreleased]

### Added

- `docs/PRIVACY.md` — модель приватности, описанная по факту, а не по замыслу. Что собирается по умолчанию (уровень Minimal §37: имя, PID, связь с родителем, времена) и что не собирается вовсе; что выключенное поле — это отсутствие поля, а не пустое значение; где лежат данные (база, каталог Agent, логи); почему редакция §38 применяется в Agent до отправки; как удалить историю. Отдельный раздел перечисляет то, что **не** защищено: база не шифруется, у loopback-API нет аутентификации, автоматического удаления нет. §69 требовал этот документ в минимуме, а `SECURITY.md` отвечает на другой вопрос — он про модель угроз, а не про то, какие данные собираются.
- `docs/DEVELOPMENT.md` — процесс по факту: окружение §64, запуск §63, уровни тестов §58, правила слоёв §50, состав CI с причинами принятых решений (`cache-python: false`, точная версия `setup-uv`, `--locked`, `PYTHONUTF8`), правила `main` из ruleset и **процедура выпуска версии** от подъёма номера до GitHub Release. Процедуры выпуска в проекте не было описано нигде: 0.0.1 выпускалась по шагам, которые существовали только в описании PR, и повторять их приходилось по памяти.
- `scripts/dev.ps1` — поднимает Core и Agent в dev-режиме (§63) одной командой: синхронизирует окружение, применяет миграции, открывает компоненты в отдельных окнах и проверяет, что Core ответил на `/health`. Окна разные намеренно: у каждого компонента свой поток JSON-логов (§35), и в одном окне две такие ленты перемешались бы. `-DryRun` печатает команды, ничего не запуская; `-Config` передаёт обоим компонентам один файл конфигурации (§36). Пути дочерним процессам передаются переменными окружения, а не подставляются в командную строку: `Start-Process` склеивает аргументы в строку, и путь с пробелом развалил бы команду на лишние аргументы.
- `scripts/test.ps1` — прогоняет тесты Core и Agent (§58) и возвращает 0, только если прошли все запрошенные наборы. Оба набора прогоняются даже если первый упал: смысл — увидеть полную картину, как в CI, а не первую ошибку. Код 2 отделён от кода 1: «тесты не запускались» и «тесты упали» — разные новости.
- Оба скрипта ищут `uv` в `PATH`, затем в `core/.venv/Scripts`, а при его отсутствии работают через интерпретатор `.venv`: окружение может быть уже готово, и падать из-за отсутствия `uv` в `PATH` скрипт не должен.
- `core/chronoscope/application/ports.py` — порты слоя приложения: `RawEventRepositoryPort`, `EventRepositoryPort` и формы данных, которыми порт обменивается (`EventQuery`, `EventPage`). Протоколы структурные, поэтому реализации в `infrastructure/` наследоваться от них не обязаны.
- [ADR-0013](docs/decisions/0013-batch-transaction.md): пакет событий принимается одной транзакцией. Решение с честно описанными издержками — отказ хранилища откатывает пакет целиком, а выигрыша по скорости нет.
- [§77.1](docs/PROJECT_SPEC.md) — **Definition of Done версии 0.0.3 «Identify»** (9 пунктов). §71 отвечает на вопрос «закончена ли функция» и о готовности версии не говорит ничего, а 0.0.3 — первая версия, где это расхождение становится опасным: `process detail` можно написать и выпустить при сломанной идентичности экземпляра, и версия будет выглядеть сделанной, не будучи ею. Пункты описывают, что именно должно быть верно: `process_instance_id` переживает `start → exit` и различает переиспользование PID (§14, инвариант 5); detail доступен по API и содержит имя, PID, boot, старт, завершение или длительность и родителя; события экземпляра и переходы из `actor`/`subject` доступны в UI; есть `chronoscope process <id>`; parent-child resolution проверен интеграционными тестами в обоих исходах (родитель наблюдался и родитель не наблюдался); реальный E2E `powershell → notepad → exit` восстанавливает цепочку через UI и API; документация честно говорит, что отсутствие завершения не доказывает, что процесс работает.
  - У каждого пункта указано, **чем он подтверждается**. Пункт, который нельзя проверить, — пожелание, а не готовность, и список, собранный из таких пунктов, к концу версии превращается в описание того, что предполагалось сделать.
  - Отдельно зафиксировано то, что в 0.0.3 **не** входит: новые источники событий, включая Windows Event Log, остаются в 0.0.4 «Observe». Пока экземпляр процесса не стал сущностью во времени, второй источник добавил бы объёма, но не смысла.
  - `docs/DEVELOPMENT.md`: гейт версии в процедуре выпуска и раздел про Definition of Done теперь требуют выполнения списка версии, а не только общего правила §71. Список, о котором узнают после выпуска, не влияет ни на что.
- **Экземпляр процесса как сущность: `GET /api/v1/processes/{process_instance_id}`** — первые два пункта Definition of Done 0.0.3 (§77.1). Отдельной таблицы процессов нет и не появилось: экземпляр — это набор событий с общим `subject_id`, и detail собирается из них на лету (`application/queries/process_detail.py`, выборка — `EventRepositoryPort.find_instance_events`). Такой detail нельзя забыть обновить при появлении нового события о том же процессе, и расходиться с историей ему негде.
  - **Терпимость к неполной истории — главное свойство модели, а не примечание к ней.** Реальны все три случая: `started ✅ exited ✅`, `started ✅ exited ❌`, `started ❌ exited ✅`. Поэтому `started_at` и `observed_start` — разные поля: событие завершения несёт `process_started_at`, и время старта процесса может быть известно **без** наблюдавшегося события запуска. Знать время и наблюдать событие — не одно и то же, и модель это не смешивает.
  - **Поля состояния нет намеренно.** `exited_at: null` означает «завершение не наблюдалось» и ничего больше: вывести из него «процесс работает» нельзя, пока коллектор может пропустить событие выхода (§8.4). Ответ на этот вопрос был бы догадкой, а догадка в истории хуже пробела.
  - `duration_ms` выводится из двух времён, а не из двух наблюдений, и остаётся `null`, если известно только одно из них — или если источник сообщил времена, противоречащие друг другу: отрицательной длительности жизни в данных не было. `parent.resolved: false` означает «родитель мог быть, но его старт не наблюдался», и при этом `parent.pid` остаётся в ответе: «родителя не было» и «родитель не наблюдался» — разные факты (§20).
  - **Предел чтения — отказ, а не усечение.** Detail собирается не более чем из 1000 событий экземпляра; при превышении отвечает `500 history_limit_exceeded`. Усечённый detail сообщил бы `observed_exit: false` о процессе, чьё завершение просто не попало в выборку, — то есть соврал бы ровно тем способом, от которого защищает вся модель.
  - **Ленты событий в ответе нет.** «Что происходило с процессом» отвечает существующий `GET /api/v1/events?subject_id=…` (§31, §32): второй способ получать те же данные означал бы вторую реализацию фильтров, пагинации и порядка сортировки.
  - **Проверено вживую**, на настоящем Core с настоящими данными, а не только тестами. Полная жизнь: `Notepad.exe` — `duration_ms: 5490`, родитель `powershell.exe` с `resolved: true`. Только запуск: тот же `Notepad.exe`, чей выход не наблюдался, — `exited_at: null`, `duration_ms: null`, `observed_exit: false`. Только завершение: событие без наблюдавшегося запуска, отправленное в живой Core, — `started_at` заполнен, `observed_start: false`, длительность посчитана. Неизвестный идентификатор — `404 not_found`, некорректный по форме — `422 invalid_input`.
  - Тестов добавлено 31: `tests/test_process_detail.py` (18), интеграционные на API (8), выборка хранилища (4), покрытие запроса индексом (1). Две ключевые проверки проверены на способность упасть: если вывести `observed_start` из наличия `started_at`, падает «завершение без наблюдавшегося запуска»; если убрать защиту от отрицательной разницы, падает «противоречащие времена не дают длительности». Тесты Core — **352**.
  - Выборка событий экземпляра читается по тому же индексу `ix_events_subject_id_timestamp(subject_id, timestamp, id)`, который появился ради сортировки списка (ADR-0014): это проверяется планом запроса, а не предполагается.
  - `docs/PROJECT_SPEC.md` §31, `docs/ARCHITECTURE.md` §2, §4 и §8, `docs/EVENT_MODEL.md` §2.4.1, `README.md`: форма ответа, отсутствие таблицы процессов и правило «время старта известно и без события запуска» описаны там, где их будут искать. §76 требует, чтобы документация соответствовала факту, а новый эндпоинт — это факт.
- **Экземпляр процесса доступен пользователю: `chronoscope process <id>` и переход из `actor`/`subject` на странице** — пункты 5 и 6 Definition of Done 0.0.3 (§77.1). API научился видеть процесс как сущность раньше, чем это стало видно человеку: CLI и страница появились в 0.0.2 именно для того, чтобы историю можно было смотреть, и версия, в которой они не умеют пользоваться главной новой сущностью, была бы выпущена наполовину.
  - CLI: `chronoscope process <process_instance_id>` показывает ровно то, что отдал API, — вычислений в CLI нет, иначе у одной сущности появилось бы второе представление. Времена и признаки наблюдения идут отдельными строками («Запуск» / «Наблюдался запуск», «Завершение» / «Наблюдался выход»), а длительность форматируется из миллисекунд с отбрасыванием дроби — «1 мин 47 с», а не «1 мин 48 с»: длительность не должна выглядеть больше измеренной. В конце подсказка `chronoscope events --subject-id …`: событий экземпляра в detail нет.
  - Страница: `actor` и `subject` в подробностях события стали переходами; панель процесса занимает место панели события и показывает идентификатор, имя, PID, boot, времена, длительность, родителя (с переходом к нему) и признаки наблюдения. Ссылка «показать события процесса» использует **существующий** фильтр `subject_id` — для этого в форме появилось поле «Субъект»; отдельного способа получить те же события у страницы нет и не появилось.
  - **Заметки вместо догадок.** Если завершение не наблюдалось, панель прямо говорит: «Это не значит, что процесс работает: Chronoscope не видел события выхода, а коллектор может его пропустить». То же — при неустановленной связи с родителем. Интерфейс — последнее место, где продукт мог бы начать выводить состояние из истории, поэтому формулировка закреплена и проверкой содержимого скрипта.
  - `README.md`: раздел «Чего Chronoscope не утверждает» — та же мысль на уровне продукта, а не отдельного эндпоинта.
  - `docs/PROJECT_SPEC.md` §31: расхождение «422 на неверную форму идентификатора против 404 на всё остальное» записано как открытый вопрос с двумя кандидатами на общее правило. Менять существующий контракт ради симметрии в 0.0.3 не стали.
  - Тесты: CLI — 8 новых (форматирование длительности и признаков наблюдения, жизненный цикл на живом Core, отсутствие выхода, неразрешённый родитель, `not_found`, `invalid_input`), страница — 4 новых статических. Поведение панели проверяется вживую браузером, а не в CI: браузерной автоматизации в проекте нет (ADR-0012), и это остаётся записанным ограничением.

### Fixed

- **Сырое событие, оставшееся без нормализованного, больше невозможно.** Пакет обрабатывался событие за событием, и каждое событие писало две записи **двумя коммитами**. Падение Core между ними оставляло в `raw_events` запись, которую повторная доставка не исправляла: Core видит знакомый `raw_event_id`, отвечает `duplicate` и нормализацию не запускает. Запись оставалась в базе навсегда, а в истории её не было — и `GET /events` показывал историю, в которой чего-то не хватает, ничем об этом не сообщая. Теперь границу задаёт пакет, и сырое событие вместе с нормализованным попадают в базу вместе ([ADR-0013](docs/decisions/0013-batch-transaction.md)).
  Тест `core/tests/test_ingest_transaction.py` проверен на способность упасть: с прежним поведением он падает ровно так, как описано, — «сырые события первого события остались в базе», `1 == 0`. Что §60 при этом не сломан, проверяется отдельно: ошибка нормализации не откатывает пакет, и сырое событие остаётся.
- `scripts/reset-dev-data.ps1` **не запускался вовсе** под Windows PowerShell 5.1: без BOM 5.1 читает `.ps1` в системной кодировке, русские комментарии и строки превращаются в мусор, и файл падает на разборе ещё до первого оператора. Под PowerShell 7 тот же скрипт работал, потому что 7 читает UTF-8 по умолчанию — поэтому дефект и не был замечен. `scripts/*.ps1` переведены в UTF-8 с BOM, а `.editorconfig` получил для них отдельное правило с объяснением, почему это отступление от общего `charset = utf-8` обосновано.
- `core/tests/test_scripts_encoding.py`: наличие BOM проверяется механически (4 теста). Правка `.editorconfig` — это пожелание, а не проверка: достаточно один раз сохранить файл в редакторе, который BOM снимает. Тест проверен на способность упасть — со снятым BOM он падает, и это видно, а не предполагается.

### Changed

- Индексы событий включают `id` — `events(timestamp, id)` и три остальных ([ADR-0014](docs/decisions/0014-event-indexes-cover-ordering.md)). Список сортируется по `timestamp DESC, id DESC` (§32), а индексы покрывали только первую компоненту сортировки, из-за чего SQLite строил временное дерево на каждом запросе страницы: `USE TEMP B-TREE FOR LAST TERM OF ORDER BY`. Миграция `0002` пересоздаёт четыре индекса под теми же именами — SQLite не умеет менять состав индекса. Индексы не добавлялись, а расширились: набор тот же, ширина больше.
  - **Что это даёт и чего не даёт.** Выигрыш зависит от плотности времен в источнике, а не от объёма истории. На 200 000 событий с разными временами разница в пределах шума (0.08 → 0.06 мс на страницу). На 200 000 событий с общим `timestamp` — том случае, который даёт источник с точностью до секунды — измерено на настоящей схеме и настоящем запросе репозитория: страница без курсора 195 → 0.52 мс, фильтр по типу 131 → 0.52, фильтр по субъекту 0.92 → 0.53. Обещать «ускорение списка событий» было бы неправдой: ускоряется не то, что и так быстрое, а снимается зависимость от распределения времен.
  - Проверяется механически: `core/tests/test_index_coverage.py` требует, чтобы в плане запроса страницы не было `TEMP B-TREE`, и проверяет план **того самого** запроса, которым пользуется репозиторий (`build_list_statement`), а не его копии в тесте. Тест проверен на способность упасть: с прежним составом индексов падают шесть проверок из семи.
  - Издержки записаны, а не умолчаны: индексы стали шире (`id` — текст около 30 байт в четырёх индексах), а миграция перестраивает их целиком, и на большой истории это тем дольше, чем больше событий.
- Приём событий работает через **единицу работы** (`UnitOfWorkPort` в `application/ports.py`, `SqliteUnitOfWork` в `infrastructure/database/`). `IngestBatch` открывает одну транзакцию на пакет, `IngestRawEvent.execute_in` принимает событие внутри чужой транзакции, а `execute` — в собственной. Логика приёма осталась одна: расходиться двум её копиям негде.
- `infrastructure/database/repositories.py`: репозиторий принимает либо движок, либо соединение. С движком он владеет транзакцией сам (как и раньше), с соединением — не управляет ею вовсе.
- Что **не** изменилось: ошибка нормализации по-прежнему не откатывает пакет (§60), идемпотентность по `raw_event_id` прежняя, формат ответа `POST /api/v1/ingest/raw-events` тот же, схема БД не менялась.
- **Замер, который опровергает ожидание.** Батчинг не ускоряет приём: на 20 000 событий 400 коммитов дают 10.4–10.5 с, а 20 000 коммитов — 10.8–13.9 с. Причина: в WAL при `synchronous = NORMAL` коммит не делает `fsync`, поэтому число коммитов почти не влияет на время, а платит за себя обслуживание индексов и рост таблицы. Ожидание ADR-0004 о батчевых вставках как о смягчении нагрузки на писателя **не подтверждено**; это записано в ADR-0013, `ARCHITECTURE.md` §6, §34 спеки и `DEVELOPMENT.md` — вместо обещания ускорения, которого нет.
- `docs/PROJECT_SPEC.md` §48 и §69, `docs/ARCHITECTURE.md`, `README.md`: `docs/PRIVACY.md` и `docs/DEVELOPMENT.md` переведены из «не создано» в «готово». Критерий §76 требует, чтобы спека соответствовала реальной архитектуре, и документ, о котором написано «его нет», — такое же расхождение, как неверный счётчик тестов.
- `SECURITY.md`, `CONTRIBUTING.md`, `agent/README.md`: ссылки на `docs/PRIVACY.md` из тех мест, где о приватности уже говорилось. `SECURITY.md` отвечает на вопрос «что считается нарушением», а `PRIVACY.md` — «какие данные собираются и что из этого не защищено»; без ссылки их легко принять друг за друга.
- `application/` больше не зависит от `infrastructure`, как требует §50. Раньше use cases импортировали модуль репозиториев напрямую, то есть направление зависимости было обратным: use case не существовал без слоя хранения, и подменить хранение (например, на память в тесте) можно было только вместе с его правкой.
  - `ListEvents`, `GetEvent` и `IngestRawEvent` зависят от портов; `GetCoreStatus` принимает путь к базе вместо объекта `CoreSettings` — ради одного поля он тянул за собой весь модуль настроек инфраструктуры.
  - `IngestRawEvent` пишет структурированные логи через стандартный `logging` с полем `event`; обработчики и JSON-формат остаются делом инфраструктуры (§35). Форма записей не изменилась — это проверено вживую на настоящем Core, а не только тестами.
  - Кодирование курсора пагинации осталось в слое хранения: его формат зависит от порядка сортировки, а клиенту он непрозрачен (§32). В порт он не переехал намеренно.
- `api/` перестал обращаться к хранилищу сам. `check_database` переехал в композиционный корень как `CoreContainer.database_state()`, поэтому `/health` и `/status` больше не трогают движок базы, а слой API не импортирует SQLAlchemy. Обработчики исключений перешли на стандартный `logging` по той же причине, что и use cases.
- `core/tests/test_layer_rules.py`: вместо одного правила — три, и детекторы проверяются на заведомо нарушающем исходнике.
  - `api/` и `application/` не импортируют `chronoscope.infrastructure`. Исключение одно — композиционный корень `api/dependencies.py`: он собирает адаптеры, и без него соединять их с use cases было бы негде.
  - `api/` и `application/` не импортируют `sqlalchemy`, `sqlite3` и `alembic`: это означало бы SQL в обход репозиториев, а §50 говорит про API это прямо.
  - Что правило действительно работает, видно по истории правки: первая версия проверки упала на `api/dependencies.py`, и исключение для композиционного корня появилось как осознанное решение, а не как ослабление до зелёного.
- `docs/ARCHITECTURE.md` §4, `docs/PROJECT_SPEC.md` §49 и §50, `docs/DEVELOPMENT.md`: описаны порты слоёв, исключение для композиционного корня и то, какие правила проверяются механически. Тесты Core — **297**.

## [0.0.2] - 2026-09-20

Цель версии — §77 «See»: увидеть поток событий удобнее, чем через `curl`. Состав — простой CLI и базовая локальная страница, то есть ровно два пункта §77; больше 0.0.2 не добавляет ничего.

Обе части проверены вживую на настоящем Core и настоящем Agent, а не только тестами. Agent наблюдал реальный запуск и завершение `notepad.exe` (pid 8596), и оба события получили **один и тот же** `subject.id` — критерий §75 продолжает выполняться и после появления интерфейсов. Все четыре команды §57 выполнены против живого Core: фильтр, курсорная пагинация и разбор подробностей работают, а `event` по несуществующему идентификатору отвечает понятным `not_found` с кодом 1, не трассировкой. Повторная отправка `shared/fixtures/ingest/ingest_batch_001.json` дала `accepted: 0, duplicates: 2` — идемпотентность §34 не изменилась.

Страница проверена на уровне HTTP: `/` перенаправляет на `/ui/`, разметка, стили и скрипт отдаются с верными типами, а запросы, которыми страница пользуется, отвечают теми же данными, что и CLI. Тесты Core — **287** (256 в 0.0.1, 278 после CLI, 287 после страницы), Agent — 97 без изменений: подъём версии его не задел.

### Added

- **CLI** (§57, первый шаг версии 0.0.2 «See»): команды `status`, `events`, `event <id>`, `doctor`. CLI — клиент локального API, а не второй доступ к базе: он обращается к Core по HTTP и потому соблюдает инвариант 10 §81. Транспорт — стандартная библиотека (`urllib`), чтобы не поднимать `httpx` в runtime-зависимости ради GET и разбора JSON (§65).

  - Список событий показывает идентификатор события. Без него `event <id>` нечем запустить, и переход «список → подробности», ради которого список и существует, был бы невозможен.

- `core/tests/test_cli.py`: модульные проверки форматирования и интеграционные — против **настоящего** Core по HTTP. Прежние интеграционные тесты Core обходились `TestClient`, то есть приложением в процессе; `urllib` из CLI так подменить нельзя, поэтому тест поднимает настоящий сервер и проверяет тот путь, которым пользуется человек.
- **Базовая страница** (§77, второй шаг 0.0.2 «See»): список событий с пагинацией, фильтрами и панелью подробностей. Отдаётся самим Core по `/ui`, а корень `/` перенаправляет туда; статика лежит в `core/chronoscope/web/` и попадает в wheel вместе с пакетом.
  - Шага сборки нет: это обычные HTML, CSS и JavaScript. Решение и его издержки — [ADR-0012](docs/decisions/0012-web-page-served-by-core.md). Коротко: у базовой страницы нет ни одной из задач, ради которых §55 выбирал React и Vite, а второй toolchain в CI и генерируемые файлы в репозитории — цена, которую §65 и §70 не позволяют платить заранее.
  - Страница и API живут на одном origin, поэтому CORS и прокси не нужны, а инвариант 10 §81 («UI не читает SQLite напрямую») соблюдается по построению.
  - Данные из API вставляются только через `textContent`: имена процессов и командные строки приходят из внешнего мира. В `core/tests/test_web_page.py` это проверяется отдельным тестом.
  - Отсутствие каталога статики не роняет Core: он остаётся рабочим API, а `/ui` отвечает 404. Это не гипотетический случай — каталог может не попасть в сборку.
- `core/tests/test_web_page.py`: отдача страницы и ресурсов, перенаправление с корня, наличие всех файлов, на которые ссылается разметка, отсутствие сборки разметки из данных и работоспособность API рядом со статикой.

## [0.0.1] - 2026-09-20

Первый работающий вертикальный срез: событие процесса Windows проходит путь от операционной системы до query API. Состав версии — §73 [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md), критерии качества — §76. Это не MVP продукта: frontend, installer и всё перечисленное в §74 остаются за его пределами.
