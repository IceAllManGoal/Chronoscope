# Changelog

Все заметные изменения Chronoscope документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версионирование — [Semantic Versioning](https://semver.org/lang/ru/). Правила версионирования до `1.0.0` описаны в §72 [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md).

## [Unreleased]

### Added

- **CLI** (§57, первый шаг версии 0.0.2 «See»): команды `status`, `events`, `event <id>`, `doctor`. CLI — клиент локального API, а не второй доступ к базе: он обращается к Core по HTTP и потому соблюдает инвариант 10 §81. Транспорт — стандартная библиотека (`urllib`), чтобы не поднимать `httpx` в runtime-зависимости ради GET и разбора JSON (§65).
  - `events` поддерживает фильтры и страницы: `--type`, `--source`, `--actor-id`, `--subject-id`, `--from`, `--to`, `--limit`, `--cursor`.
  - `doctor` проверяет доступность Core, применённую схему, расхождение версий CLI и Core и наличие данных, а к каждой проблеме даёт команду для исправления.
  - Список событий показывает идентификатор события. Без него `event <id>` нечем запустить, и переход «список → подробности», ради которого список и существует, был бы невозможен.
  - Время выводится в местной зоне: §24 оставляет локальную timezone заботе вывода, а не хранилища.
- `core/tests/test_cli.py`: модульные проверки форматирования и интеграционные — против **настоящего** Core по HTTP. Прежние интеграционные тесты Core обходились `TestClient`, то есть приложением в процессе; `urllib` из CLI так подменить нельзя, поэтому тест поднимает настоящий сервер и проверяет тот путь, которым пользуется человек.
- **Базовая страница** (§77, второй шаг 0.0.2 «See»): список событий с пагинацией, фильтрами и панелью подробностей. Отдаётся самим Core по `/ui`, а корень `/` перенаправляет туда; статика лежит в `core/chronoscope/web/` и попадает в wheel вместе с пакетом.
  - Шага сборки нет: это обычные HTML, CSS и JavaScript. Решение и его издержки — [ADR-0012](docs/decisions/0012-web-page-served-by-core.md). Коротко: у базовой страницы нет ни одной из задач, ради которых §55 выбирал React и Vite, а второй toolchain в CI и генерируемые файлы в репозитории — цена, которую §65 и §70 не позволяют платить заранее.
  - Страница и API живут на одном origin, поэтому CORS и прокси не нужны, а инвариант 10 §81 («UI не читает SQLite напрямую») соблюдается по построению.
  - Данные из API вставляются только через `textContent`: имена процессов и командные строки приходят из внешнего мира. В `core/tests/test_web_page.py` это проверяется отдельным тестом.
  - Отсутствие каталога статики не роняет Core: он остаётся рабочим API, а `/ui` отвечает 404. Это не гипотетический случай — каталог может не попасть в сборку.
- `core/tests/test_web_page.py`: отдача страницы и ресурсов, перенаправление с корня, наличие всех файлов, на которые ссылается разметка, отсутствие сборки разметки из данных и работоспособность API рядом со статикой.

### Changed

- Версия поднята до 0.0.2 в `core/pyproject.toml`, `core/chronoscope/__init__.py` и `agent/src/Chronoscope.Agent/AgentInfo.cs`.
- Вывод CLI на русском, хотя пример §57 приведён на английском. Причина не в вольности: CLI показывает и сообщения самого Core, а они на русском — английская подпись над русским текстом ошибки читалась бы как небрежность. Разделитель разрядов — пробел, как принято в русской типографике.
- `chronoscope status` не показывает состояние Agent как «подключён», хотя это есть в примере §57: Core не отслеживает Agent в этой версии (§31) и честно возвращает `null`. Выдуманное «подключён» стало бы единственным местом продукта, где состояние не измерено, а придумано.
- `docs/ARCHITECTURE.md` §4 и §49 `docs/PROJECT_SPEC.md`: `cli/` добавлен в структуру Core с оговоркой, что это не слой, а внешний клиент.
- `core/chronoscope/main.py` монтирует статику и перенаправляет корень на неё: без перенаправления человек, открывший единственный известный адрес, получил бы 404 и решил, что Core не работает.
- `frontend/README.md` описывает фактическое состояние: первый интерфейс появился в 0.0.2, но не здесь, а в `core/chronoscope/web/`; каталог остаётся зарезервированным под стек §55, который понадобится к 0.1.0 «Timeline».

### Fixed

- `chronoscope.cli.client.CoreRejected` не сохранял текст ошибки в атрибуте, из-за чего обращение к нему в обработчике превращало понятное сообщение в трассировку. Найдено при проверке пути «событие не найдено» вживую: до исправления несуществующий идентификатор давал `AttributeError` вместо `not_found`.

## [0.0.1] - 2026-09-20

Первый работающий вертикальный срез: событие процесса Windows проходит путь от операционной системы до query API. Состав версии — §73 [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md), критерии качества — §76. Это не MVP продукта: frontend, installer и всё перечисленное в §74 остаются за его пределами.

Критерий готовности §75 пройден полностью и проверен вживую с настоящим Agent: `/health` отвечает, Agent наблюдает запуск и завершение `notepad.exe`, оба события получают **один и тот же** `process_instance_id`, история переживает перезапуск Core, повторная доставка `RawEvent` не создаёт дубликат.

Известное ограничение версии: полнота наблюдения за процессами **не гарантирована**. Механизм на собственных событиях WMI с интервалом опроса в секунду может пропустить короткоживущий процесс — измерено (5 из 5 для `cmd.exe`, 4 из 5 для `notepad.exe`) и описано вместе с направлением решения в [`agent/README.md`](agent/README.md).

### Added

- `docs/ARCHITECTURE.md` — компоненты, слои Core, поток данных, инварианты.

- **CI на GitHub Actions** (`.github/workflows/ci.yml`): Windows-раннер (ADR-0006), Python 3.13, `uv sync --all-groups --locked`, `alembic upgrade head`, `pytest`. Запускается на каждый pull request и на `main`. До этого изменение не проверял никто, кроме автора: ruleset гарантировал форму изменений, но не их работоспособность.
- Тест `core/tests/test_layer_rules.py`: правила слоёв §50 проверяются механически — `domain/` и `normalization/` не должны импортировать FastAPI, SQLAlchemy, SQLite, HTTP и Windows API. ADR-0008 признавал, что эти границы держатся только дисциплиной и ревью, а ревью — не компилятор.
- **Chronoscope Agent** — второй runtime-компонент (§90 шаги 13–16): решение C#/.NET из трёх проектов, `ProcessCollector` на WMI, ограниченный буфер и доставка пакетами. 97 тестов.
  - `Ulid` — каноническая форма, совместимая с валидацией Core. Эталоны в тестах получены выполнением `chronoscope.domain.ids.ulid_from`, то есть совместимость двух независимых реализаций проверяется, а не предполагается. Сверка сразу нашла дефект: 80 бит случайной части собирались так, что биты 16–63 оставались нулями — идентификатор сохранял форму, но терял энтропию в середине. Проверка формы (`IsValid`) этого не находила.
  - `RawEvent` и его сериализация строго по `shared/schemas/raw-event.schema.json`; время пишется своим конвертером, потому что сериализатор .NET по умолчанию отдаёт смещение, а схема требует суффикс `Z`.
  - Конфигурация TOML: один файл на проект (§36), адрес Core берётся из секции `[core]`, секции другого компонента пропускаются, неизвестные ключи в своих секциях отвергаются. Адрес приёма проверяется на loopback — иначе собранные сведения уходили бы за пределы машины (§33, ADR-0007).
  - `host_id` хранится в файле и не выводится из железа (§15); `boot_id` выводится из времени загрузки ОС детерминированно (§16).
  - Транспорт (§34): ограниченная очередь со счётчиком потерь, отправка пакетами по размеру и по интервалу, at-least-once с экспоненциальной задержкой, различение повторяемых и необратимых отказов, последняя отправка накопленного при завершении.
  - Структурированные JSON-логи Agent (§35).
- `agent/README.md`: запуск, состав проектов, ключи конфигурации, приватность по умолчанию, **измеренная полнота наблюдения** и известные ограничения.
- [ADR-0011](docs/decisions/0011-agent-project-structure.md): три проекта Agent и явная платформенная цель сборки.
- Джоба `Agent tests` в CI: Windows-раннер, .NET SDK 8, сборка и тесты.

### Fixed

- `POST /api/v1/ingest/raw-events`: пакет, отвергнутый целиком **только** из-за неподдерживаемой `schema_version`, теперь отвечает `unsupported_schema_version`, а не `invalid_input`. Раньше один и тот же дефект данных описывался разными машинными кодами в зависимости от состава пакета, тогда как §52 требует отличать несовместимость версий от обычного невалидного payload.
- `core/alembic.ini`: файл содержал русские комментарии в UTF-8, а Alembic читает его в locale-кодировке (`alembic/util/compat.py`: `file_config.read(..., encoding="locale")`). На Windows с кодовой страницей cp1252 команда `uv run alembic upgrade head` из README падала с `UnicodeDecodeError`, тогда как на cp1251 те же байты молча декодировались в мусор — поэтому локально дефект не был виден. Это противоречило ADR-0006: команда миграций не работала на Windows с западноевропейской локалью. Комментарии переписаны на ASCII, ограничение задокументировано в самом файле, регрессия закрыта тестом `TestAlembicConfig::test_ini_is_pure_ascii`. Дефект нашёл CI на втором прогоне.
- `cache-python` в CI отключён: кэширование каталога managed-интерпретатора ломало джобу `Core tests` на Windows (`failed to remove directory ... The directory name is invalid`, os error 267). Дефект был внесён в `main` предыдущей правкой CI и проявился только на втором прогоне, когда кэш уже существовал.
