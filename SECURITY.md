# Security Policy

## Модель безопасности Chronoscope

Chronoscope — локальный продукт. Его поверхность атаки принципиально узкая, и это осознанное архитектурное решение (§33, §66 спеки, [ADR-0007](docs/decisions/0007-local-only-api.md)):

- Core слушает **только** `127.0.0.1`, не `0.0.0.0`;
- отсутствует API для удалённого выполнения кода;
- отсутствует endpoint для произвольного SQL;
- отсутствует shell endpoint;
- payload строго валидируется, размер запроса ограничен;
- путь к БД задаётся конфигурацией и никогда не приходит от HTTP-клиента;
- чувствительные данные минимизируются в логах.

Chronoscope **не является** средством защиты. Он не предотвращает заражения, не блокирует процессы и не заменяет Windows Defender (§5.1).

Этот документ отвечает на вопрос «что считается нарушением безопасности». На вопрос «какие данные вообще собираются, где лежат и что из этого не защищено» отвечает [`docs/PRIVACY.md`](docs/PRIVACY.md) — в том числе перечисляет незащищённое прямо, а не умалчивает.

## Что считается уязвимостью

Принимаются сообщения о:

- выполнении кода или команд через ingest payload, заголовки или query-параметры;
- SQL injection и любом обходе слоя репозиториев;
- path traversal, записи или чтения файлов за пределами разрешённых путей;
- привязке API к не-loopback интерфейсу или обходе этой привязки;
- раскрытии чувствительных данных: утечке командных строк, токенов и паролей в логи, ответы API или экспорт вопреки настройкам privacy;
- отказе в обслуживании, приводящем к потере уже собранных данных или повреждению БД при штатных сценариях;
- небезопасном хранении или обработке данных в `data/`.

## Что уязвимостью не считается

- Отсутствие антивирусных функций, детектирования malware и блокировки процессов.
- Ситуация, когда злоумышленник уже имеет права локального администратора: в этом случае он может читать и изменять локальные данные Chronoscope напрямую.
- Отсутствие аутентификации на loopback-интерфейсе: это осознанное состояние 0.0.1, локальный shared secret между Agent и Core запланирован позже (§33).
- Ограниченность redaction: автоматическая редакция не может быть идеальной, поэтому пользователю доступно полное отключение чувствительных полей (§38).

## Как сообщить

Основной канал — **GitHub Private Vulnerability Reporting** в этом репозитории: вкладка *Security* → *Report a vulnerability*. Сообщение видит только мейнтейнер.

Резервный канал — email: **nur.2002228@gmail.com**. Используй его, если приватный канал GitHub недоступен.

Пожалуйста, не открывай публичный Issue с деталями уязвимости. Если ни один приватный канал не сработал, создай Issue без технических подробностей и попроси связаться напрямую.

Полезно приложить:

- версию (`0.0.1` и commit SHA);
- конфигурацию, если она влияет на воспроизведение;
- шаги воспроизведения или PoC;
- оценку влияния;
- предложение по исправлению, если есть.

## Поддерживаемые версии

Проект находится в стадии `0.x`: поддерживается только ветка `main`. Отдельные ветки релизов не сопровождаются. Это изменится к `1.0.0`.

## Ожидания по срокам

Проект развивается без выделенной команды безопасности. Подтверждение получения — по возможности в течение нескольких дней. Пожалуйста, отнесись к этому с пониманием и не раскрывай детали публично до исправления.

## Инварианты, которые не должны нарушаться

Любое изменение, ослабляющее эти правила, требует отдельного ADR (§81):

1. Core не зависит от Windows API.
2. API по умолчанию local-only.
3. Cloud не является обязательной зависимостью.
4. UI не читает SQLite напрямую.
5. БД изменяется только через миграции.
6. Один сломанный event не останавливает pipeline.
