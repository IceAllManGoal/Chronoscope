# Development

Как поднять Chronoscope, проверить изменение и выпустить версию. Правила вклада — в [CONTRIBUTING.md](../CONTRIBUTING.md); здесь то, что нужно знать про **процесс**, а не про то, как оформлять PR.

Документ описывает фактическое состояние после 0.0.2. Если он разойдётся с фактом — правым считается факт: §76 требует, чтобы документация соответствовала реальной архитектуре.

## Окружение (§64)

```text
Windows
Git
Python 3.13+
.NET SDK 8+          — для Agent
PowerShell
uv                   — окружение Core
```

Docker не требуется и не используется: Chronoscope — локальный продукт, а Agent обязан быть Windows-native процессом, поэтому контейнеризация не является полезной целью сама по себе ([ADR-0010](decisions/0010-no-containerization-in-0.0.1.md)). Windows нужен как среда разработки, а не только как цель: платформенная граница Agent проверяется компилятором, и на другой ОС часть решения просто не собирается ([ADR-0006](decisions/0006-windows-first.md)).

**Про PowerShell.** Рекомендуемый хост — PowerShell 7 (`pwsh`): он читает скрипты в UTF-8 по умолчанию, и в примерах указан именно он. Скрипты из `scripts/` работают и под Windows PowerShell 5.1, который есть в системе всегда, — ради этого они записаны в UTF-8 **с BOM**: без BOM 5.1 читает файл в системной кодировке, русский текст превращается в мусор, и скрипт падает на разборе. Подробнее — в [`scripts/README.md`](../scripts/README.md).

**Про `uv`.** Скрипты ищут его в `PATH`, затем в `core/.venv/Scripts`. Если `uv` нет вовсе, а окружение уже создано, `dev.ps1` работает через интерпретатор `.venv`, а `test.ps1` честно сообщает, что тесты Core не запускались (код 2), вместо того чтобы показать пустой успех.

## Первый запуск

Core — первый терминал (§63):

```powershell
cd core
uv sync --all-groups
uv run alembic upgrade head     # Core не применяет миграции сам (инвариант 11 §81)
uv run python -m chronoscope
```

Agent — второй терминал:

```powershell
dotnet run --project agent/src/Chronoscope.Agent.Host
```

Точка входа — `Chronoscope.Agent.Host`: композиционный корень обязан знать и ядро, и платформенного коллектора ([ADR-0011](decisions/0011-agent-project-structure.md)).

Обе команды за одну: [`scripts/dev.ps1`](../scripts/README.md) синхронизирует окружение, применяет миграции и открывает компоненты в отдельных окнах — окна разные, потому что у каждого свой поток JSON-логов (§35), а смешанные логи двух процессов читать нельзя. Скрипт проверяет, что Core действительно ответил на `/health`, и различает «не поднялся» и «не запускался» кодами возврата 1 и 2. Параметры: `-Core`, `-Agent`, `-Config`, `-SkipSync`, `-SkipMigrate`, `-HealthTimeout`, `-DryRun`.

Проверка, что всё живо:

```powershell
curl http://127.0.0.1:7342/api/v1/health          # Core и база
curl http://127.0.0.1:7342/api/v1/events          # события
cd core; uv run chronoscope doctor                # то же, но с расшифровкой проблем
```

Страница — http://127.0.0.1:7342/ui/, интерактивная документация API — http://127.0.0.1:7342/docs.

### Конфигурация

Один файл на весь проект (§36): Core читает `[core]` и `[storage]`, Agent — `[core]`, `[agent]`, `[collectors.process]` и `[privacy]`, секции другого компонента пропускаются. Путь задаётся переменной `CHRONOSCOPE_CONFIG`, иначе берётся `chronoscope.toml` в текущем каталоге. Пример — [`core/chronoscope.example.toml`](../core/chronoscope.example.toml).

Две ошибки в конфигурации обнаруживаются при загрузке, а не в работе: **неизвестный ключ внутри своей секции** (опечатка выглядела бы как «настройка не применилась») и **адрес вне loopback** (§33, [ADR-0007](decisions/0007-local-only-api.md)).

## Тесты (§58)

```powershell
pwsh scripts/test.ps1              # оба набора, как в CI

cd core
uv run pytest                      # 374 теста Core

cd ../agent
dotnet test Chronoscope.Agent.sln  # 137 тестов Agent
```

[`scripts/test.ps1`](../scripts/README.md) прогоняет оба набора даже если первый упал: смысл — увидеть полную картину, а не первую ошибку, и так же устроен CI. Код возврата различает «упало» (1) и «не запускалось» (2): смешивать эти новости в один код нельзя, иначе отсутствие окружения выглядело бы упавшим тестом.

Уровни и то, чем они закрыты:

| Уровень | Что проверяет |
|---|---|
| unit | нормализатор, объекты-значения, валидация, генерация идентификаторов, правила домена |
| contract | совместимость Agent ↔ Core против схем `shared/schemas/` и фикстур `shared/fixtures/` |
| repository | временная SQLite: вставка, дубликаты, запросы, порядок, миграции |
| integration | `POST raw event` → сохранение → нормализация → `GET event` |
| e2e | сценарий §75 целиком, вживую, с настоящим Agent |

Интеграционные тесты CLI поднимают **настоящий** сервер по HTTP, а не `TestClient`: CLI ходит через `urllib`, и подменить его приложением в процессе нельзя. Проверка, которая подменяет транспорт, проверяет не тот путь, которым пользуется человек.

Правила слоёв §50 проверяются механически — `core/tests/test_layer_rules.py` читает импорты через `ast`, а не импортирует модули: импорт поймал бы только падение в рантайме и пропустил бы зависимость внутри функции.

## Правила слоёв (§50)

```text
domain/         не зависит от FastAPI, SQLAlchemy, SQLite, HTTP и Windows
normalization/  то же; доступ к сохранённым данным — через порт, а не через репозиторий
application/    use cases: координируют репозитории, нормализаторы и транзакцию;
                хранилище видят через порты из application/ports.py
infrastructure/ конкретные технологии: SQLite, файловая система, логи, конфигурация
api/            HTTP: валидация транспортной схемы, вызов use case, ответ; SQL не пишет
```

Правила проверяются механически (`core/tests/test_layer_rules.py`), а не только на ревью: `domain/` и `normalization/` не должны импортировать технологии, `application/` и `api/` — слой инфраструктуры и хранилище. Единственное исключение — композиционный корень `api/dependencies.py`: он соединяет адаптеры с use cases, и без него соединять было бы негде. Сам детектор тоже проверяется, на заведомо нарушающем исходнике: правило, которое не может сработать, — это не правило, а комментарий.

При добавлении use case помни: он не должен знать про SQLite. Порты объявляются в `application/ports.py`, реализация — в `infrastructure/`.

Если use case пишет в базу, он работает через единицу работы (`UnitOfWorkPort`, реализация — `SqliteUnitOfWork`): одна транзакция на вызов use case, а для пакета — на пакет ([ADR-0013](decisions/0013-batch-transaction.md)). Репозитории, полученные от единицы работы, коммитят не сами: граница транзакции одна, и владеет ею тот, кто её открыл. Так сырое событие и нормализованное попадают в базу вместе, а не с окном между ними.

Замеры, которые стоит знать перед изменением приёма: батчинг **не** ускоряет запись. На 20 000 событий 400 коммитов дают 10.4–10.5 с, а 20 000 коммитов — 10.8–13.9 с: в WAL при `synchronous = NORMAL` коммит не делает `fsync`, и число коммитов почти не влияет на время. Стоимость определяется обслуживанием индексов и размером таблицы, поэтому оптимизацию приёма надо начинать с измерения, а не с уменьшения числа коммитов.

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) запускается на каждый pull request и на push в `main`. Две джобы, обе на `windows-latest`:

| Джоба | Что делает |
|---|---|
| `Core tests` | `node --check` для JavaScript страницы, `uv sync --all-groups --locked`, `uv run alembic upgrade head`, `uv run pytest` |
| `Agent tests` | `dotnet build`, затем `dotnet test --no-build` |

Имя джобы — это имя проверки в ruleset. Переименование ломает уже настроенное требование, поэтому меняется осознанно.

Проверка разметки страницы отдельным шагом нужна потому, что у страницы нет сборки ([ADR-0012](decisions/0012-web-page-served-by-core.md)): опечатку в её JavaScript не поймал бы ни компилятор, ни тесты — тесты проверяют то, что отдаёт сервер, а исполняется скрипт в браузере.

Несколько решений в CI стоили времени и записаны здесь, чтобы не повторяться:

- **`cache-python: false`.** Кэширование managed-интерпретатора uv ломает джобу на Windows: внутри каталога остаётся ссылка `cpython-3.13-...`, её цель в кэш не попадает, и следующий шаг падает с `os error 267`. Проверено на практике.
- **Точная версия `setup-uv`.** Начиная с v8 Astral не публикует плавающие теги вида `@v10`; ссылка на несуществующий тег валит workflow на этапе подготовки действий.
- **`PYTHONUTF8: "1"`.** Без этого консоль на Windows спотыкается о кириллицу в выводе.
- **`--locked`.** Если `uv.lock` разошёлся с `pyproject.toml`, это ошибка, а не повод молча пересобрать окружение и проверить не то, что зафиксировано.

## Ветки, коммиты, pull requests

`main` защищён ruleset'ом, и обойти его нельзя даже владельцу: обязателен pull request, обязательны зелёные `Core tests` и `Agent tests`, требуется линейная история, разрешены только squash и rebase, force-push и удаление ветки запрещены. Проверки должны быть актуальны относительно `main`: устаревшая ветка не пройдёт гейт, даже если её прогон был зелёным.

Это не формальность: до появления CI изменение не проверял никто, кроме автора — ruleset гарантировал форму изменений, но не их работоспособность.

Содержательные правила — имена веток, содержание коммитов, состав PR — в [CONTRIBUTING.md](../CONTRIBUTING.md).

## Выпуск версии

Порядок, по которому выпущены 0.0.1 и 0.0.2. Тег ставится на **merge-коммит** релизного PR, а не на ветку: версия — это состояние `main` после слияния, а не состояние ветки.

1. **Версия.** Поднимается в трёх местах: `core/pyproject.toml`, `core/chronoscope/__init__.py`, `agent/src/Chronoscope.Agent/AgentInfo.cs`. После изменения `pyproject.toml` нужен `uv lock`: иначе `uv sync --locked` в CI упадёт, и падение будет выглядеть несвязанным с версией.
2. **Гейт версии.** Сценарий версии проверяется **вживую**, на настоящих компонентах, а не только тестами. Для 0.0.1 это §75; для 0.0.2 — четыре команды CLI и страница рядом с настоящим Agent. Если у версии описан свой Definition of Done (для 0.0.3 — §77.1, для 0.0.4 — §77.2), выпуск требует его выполнения: пункты проверяются **до** релизного PR, а не после, иначе список превращается в описание того, что предполагалось сделать. Если что-то не проверялось, это записывается как непроверенное, а не умалчивается. Отдельно у 0.0.4: пункт 11 требует **часового измерения** с обоими источниками, поэтому выпуск запрещён, если живой сценарий или первый час измерения не выполнены — версия без числа нагрузки была бы догадкой о ней.
3. **Релизный PR.** Ветка `chore/release-X.Y.Z` от `main`: `CHANGELOG.md` — `[Unreleased]` переезжает под `[X.Y.Z]` с датой (так требует Keep a Changelog), `[Unreleased]` остаётся пустым под следующую версию; `README.md` — статус и число тестов приводятся к факту.
4. **Слияние** после зелёных проверок: squash или rebase.
5. **Тег** — аннотированный, на merge-коммит:
   ```powershell
   git tag -a vX.Y.Z -F tag-message.txt <merge-commit>
   git push origin vX.Y.Z
   ```
6. **GitHub Release:** имя вида `X.Y.Z — <суть версии>`, описание — вступление плюс раздел `[X.Y.Z]` из CHANGELOG, `prerelease` включён: до `1.0.0` версии не объявляются готовыми продуктами.

Известное ограничение версии записывается **в описание выпуска**, а не только в документацию компонента: тот, кто берёт версию, должен узнать об ограничении из её описания, а не обнаружить его на своей истории.

## Измерения (§61)

§61 требует измерять, а не верить на слово, и §77.2 (пункт 11) делает измерение условием выпуска 0.0.4. Протокол одного измерения:

1. Поднять **изолированную конфигурацию** — свой порт, своя база, свой каталог данных Agent. Измерение не должно смешиваться с рабочими данными: его результат потом сравнивают с числами, а не пересказывают.
2. Включить источники в том виде, в каком их получит пользователь, и **без семантической фильтрации**: только приватность по умолчанию (`capture_message = false`), без фильтров по уровню, провайдеру или `event_id`. Фильтр до измерения означал бы измерение своей гипотезы, а не источника.
3. Дать системе поработать не менее часа обычной работы.
4. Записать: событий в час по каждому источнику; распределение по `provider` и по `event_id`; сырых событий в час; рост файла базы; CPU и память Agent и Core; отзывчивость API и страницы.
5. Положить результат в раздел версии в `CHANGELOG.md`. Следующая версия сравнивается с числом, а не с воспоминанием.

Что делать с результатом — отдельное решение. Высокая плотность сама по себе проблемой не является: она становится проблемой нагрузкой, а не количеством строк. Фильтр по уровню или провайдеру вводится по измеренному распределению и как отдельное изменение, а не по ощущению «слишком много строк».

### Первый baseline 0.0.4 (2026-10-10)

Изолированная конфигурация: `127.0.0.1:7411`, своя база, каналы `System` и `Application`, `capture_message = false`, никаких фильтров по уровню, провайдеру и `event_id`. Наблюдение — **59.9 минуты**, то есть ровно час (07:43:51Z → 08:43:44Z), на настоящих Core и Agent и на настоящем журнале.

| Что | Значение |
|---|---|
| Событий журнала | **113** (113 в час): `Application` 99, `System` 14 |
| Событий процессов | **162** (162 в час) |
| Сырых событий всего | 275, и столько же нормализованных: ни одного сырого без события |
| Доминирующий провайдер | `Microsoft-Windows-RestartManager` — 88 из 113 (78 %), поровну 10000 и 10001 |
| Остальные провайдеры | `IsolatedUserMode` 7, `Security-SPP` 6, `WindowsUpdateClient` 4, `Kernel-Power` 3, `System Restore` 2, `VSS` 2, `Application` 1 |
| Уровни записей | 4 (Information) — 111, 2 (Error) — 2 |
| Рост файлов базы | 4.24 МиБ за час: 268 КиБ основного файла и 4.0 МиБ WAL на момент замера (контрольная точка не выполнялась) |
| CPU Agent | 1.6 → 2.5 с за 49 минут сэмплирования, то есть около секунды в час |
| Память Agent | медиана 63.3 МиБ, максимум 66.4 МиБ |
| CPU Core | 3.0 → 8.6 с за то же окно |
| Память Core | медиана 69.1 МиБ, максимум 69.8 МиБ |
| Отзывчивость API | `GET /events?limit=50`: медиана 11.6 мс, максимум 20.9 мс (82 замера) |
| Отзывчивость страницы | `/ui/`: медиана 18.1 мс, максимум 31.2 мс |

Две оговорки, без которых числа значат не то, что кажутся. Час измерялся **на занятой машине**: сборки, прогоны тестов и браузеры шли параллельно, и именно они дали 78 % записей журнала — Restart Manager регистрирует сессии, когда файлы заменяются при сборке. Это не «поток журнала у тихого пользователя», а поток на машине, где что-то делают, и следующая версия сравнивается с этими числами с той же поправкой. Вторая: нагрузка измерена на **Debug**-сборках Agent, потому что живой прогон шёл на них; Release-сборка не измерялась.

Что из этого следует для решения о фильтрах: плотность проблемой не оказалась — 275 событий в час при стабильной памяти и отзывчивости 11–31 мс, — но распределение показало, что один провайдер дал 78 % потока. Фильтр по нему не введён: он фильтровал бы чужую (мою) активность, а не свойство источника. Решение остаётся отдельным и требует измерения на машине без сборок.

## Локальные данные

`data/` в корне репозитория — база и её служебные файлы; в git каталог не попадает. Сброс:

```powershell
pwsh scripts/reset-dev-data.ps1
```

Скрипт удаляет только содержимое `data/` и не трогает код, миграции, фикстуры и конфигурацию. Запущенный Core держит базу открытой — на Windows файл может не удалиться, поэтому Core останавливают первым.

Проверять изменение версии лучше на **изолированной** конфигурации — свой порт, своя временная база, свой `data_directory` у Agent, — а не на dev-данных: тогда проверку можно повторить с нуля, а результат не зависит от того, что накопилось в рабочей базе. Так проверялись 0.0.1 и 0.0.2.

## Расхождение документации и факта

Расхождение — дефект, а не мелочь (§76). Изменение, меняющее факт, меняет и документ в том же PR:

| Документ | Что в нём обязано быть верным |
|---|---|
| [`README.md`](../README.md) | статус версии, число тестов, команды запуска |
| [`docs/PROJECT_SPEC.md`](PROJECT_SPEC.md) | §48 — фактическое состояние репозитория; §77 — что уже сделано |
| [`docs/ARCHITECTURE.md`](ARCHITECTURE.md) | слои, состав компонентов, инварианты |
| [`docs/EVENT_MODEL.md`](EVENT_MODEL.md) | модель события и идентификаторов |
| [`docs/PRIVACY.md`](PRIVACY.md) | что собирается, что хранится, что не защищено |
| [`SECURITY.md`](../SECURITY.md) | модель безопасности и процедура сообщения об уязвимости |
| [`CHANGELOG.md`](../CHANGELOG.md) | что вошло в версию |
| [`docs/decisions/`](decisions/) | почему решение принято и чем за него платят |

История проекта показывает, что расхождения находятся: устаревшие счётчики тестов, неработавшая на Windows команда миграций из-за кодировки `alembic.ini`, «число проектов Agent» в спеке против фактических трёх. Все они были исправлены, а не объяснены.

## Отладка

- **Логи** — структурированный JSON в stdout обоих процессов (§35). Содержимое payload в них не пишется.
- **`chronoscope doctor`** — проверяет доступность Core, применённую схему, расхождение версий CLI и Core и наличие данных, и к каждой проблеме даёт команду для исправления.
- **`GET /api/v1/status`** — объёмы данных и размер базы.
- **`/docs`** — OpenAPI: можно отправить событие и посмотреть ответ, не поднимая Agent.
- **`schema_incomplete`** в логе при старте — схема не применена: `uv run alembic upgrade head`.
- **CLI возвращает код 2**, если Core не отвечает, и подсказывает команду запуска: это не ошибка CLI, а состояние среды.
- **Миграции и Windows.** `alembic.ini` обязан оставаться в ASCII: Alembic читает его в locale-кодировке, и на Windows с западноевропейской локалью команда падала с `UnicodeDecodeError` — при русской локальной кодировке тот же дефект был не виден. Регрессия закрыта тестом.

## Зависимости (§65)

Зависимость не добавляется ради небольшого удобства. Для существенной нужно понимать, зачем она, её лицензию, состояние проекта, транзитивные зависимости и возможность замены. Особенная осторожность — с Windows-хуками, перехватом трафика, драйверами, нативными библиотеками и службами с повышенными правами.

Пример действующего правила: CLI работает на стандартной библиотеке (`urllib`), потому что для GET, разбора JSON и таймаута зависимость не нужна, а `httpx` остаётся dev-зависимостью — для тестов.

## Definition of Done

Полный список — §71 и [CONTRIBUTING.md](../CONTRIBUTING.md). Коротко: код работает, ошибки обработаны, тесты нужного уровня написаны, документация обновлена, регрессии приватности нет, способ проверить вручную существует, миграция создана при изменении схемы, версия контракта рассмотрена при изменении формата.

Это правило отвечает на вопрос «закончена ли функция». У версии может быть свой список — он его дополняет и лежит рядом с её объёмом в §77: для 0.0.3 это [§77.1](PROJECT_SPEC.md). Версия выпускается, только когда выполнены оба.
