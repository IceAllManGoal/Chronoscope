# Privacy

Chronoscope записывает историю работы компьютера, а такая история чувствительна сама по себе: она говорит, какие программы запускались, когда и в каком порядке. Поэтому приватность здесь — не режим, который включают позже, а свойство по умолчанию (§6.2). Этот документ описывает **фактическое состояние 0.0.2**, а не намерение: §69 требует, чтобы документация соответствовала факту, а обещание вместо описания — худший вид документации о приватности.

## Коротко

- Данные остаются на компьютере. Аккаунта, облака и обязательного интернет-соединения нет (§6.1).
- API слушает только loopback `127.0.0.1`. Bind на другой адрес отвергается на уровне конфигурации, а не на уровне дисциплины (§33, [ADR-0007](decisions/0007-local-only-api.md)).
- По умолчанию собирается уровень **Minimal** (§37): имя процесса, PID, связь с родителем, времена. Путь, командная строка и пользователь **не собираются**.
- Выключенное поле означает **отсутствие поля** в событии, а не пустое значение. «Не собирали» и «не удалось получить» — разные вещи, и пустая строка стёрла бы это различие.
- Автоматического удаления истории нет (§39). Как удалить вручную — ниже.
- Отдельный раздел перечисляет то, что **не защищено**. Молчание об этом было бы формой обещания.

## Что собирается в 0.0.2

| Данные | По умолчанию | Где настраивается |
|---|---|---|
| Имя процесса | собирается | — |
| PID | собирается | — |
| PID родителя и признак найденной связи (`parent_resolved`) | собирается | — |
| Времена: старт процесса, момент наблюдения | собирается | — |
| Путь к исполняемому файлу | **не собирается** | `[collectors.process] capture_path` |
| Командная строка | **не собирается** | `[collectors.process] capture_command_line` |
| SID пользователя | **не собирается** | `[collectors.process] capture_user` |

Первые четыре строки — это уровень Minimal §37, и отключить их нельзя: без имени и PID событие процесса не имеет смысла. Остальные три строки — уровень Standard; они выключены по умолчанию, хотя пример §36 показывает `capture_command_line = true`. Выбран более осторожный вариант: §6.2 объявляет privacy by default, а §37 сам предупреждает, что командная строка может содержать токены, пароли и приватные пути.

Идентификаторы машины и загрузки (`host_id`, `boot_id`) тоже сохраняются — иначе события разных машин нельзя было бы различить. `host_id` хранится в файле и **не выводится из железа** (§15), `boot_id` выводится из времени загрузки ОС детерминированно (§16).

## Что не собирается вовсе

Ни одного коллектора, кроме наблюдения за процессами, в 0.0.2 нет. Это не «выключено по умолчанию», а **не реализовано**: сеть, DNS, файлы, реестр, службы, драйверы, обновления, производительность, содержимое окон и документов, а также то, что §5 выносит в не-цели напрямую — нажатия клавиш, снимки экрана, содержимое трафика.

§8.3 перечисляет будущие коллекторы. Появление любого из них обязано сопровождаться правкой этого документа: приватность — не следствие архитектуры, а то, что кто-то должен проверить.

## Redaction (§38)

Шаблоны `[privacy] redact_command_line_patterns` — регулярные выражения, совпадения которых заменяются на `***`. Редакция применяется **в Agent, до отправки**: в Core и в хранилище попадает уже отредактированное значение, исходного там не остаётся.

Редакция работает только над командной строкой и только когда её вообще собирают. Автоматическая редакция не может быть полной — это признаёт и §38, — поэтому основной механизм защиты не шаблоны, а выключенная по умолчанию командная строка.

## Где лежат данные

| Что | Где |
|---|---|
| SQLite-база Core: `raw_events` и `events` | `[storage] database_path`, по умолчанию `./data/chronoscope.db`, рядом служебные файлы WAL и SHM |
| Сырые события (§29) | там же, отдельной таблицей: payload целиком — он нужен для переобработки и разбора дефектов нормализаторов |
| Нормализованные события | там же: атрибуты в JSON, включая `command_line`, **если** его собирают |
| `host_id` Agent | `[agent] data_directory`, по умолчанию `%LOCALAPPDATA%\Chronoscope` |
| Буфер неотправленных событий | только в памяти процесса Agent, на диск не пишется |
| Логи | stdout обоих процессов, структурированный JSON (§35) |

## Что попадает в логи

Логи пишут идентификаторы, типы, счётчики и тексты ошибок: `raw_event_id`, `event_id`, `collector`, `payload_type`, размеры и коды ответа Core. **Содержимое payload в логи не пишется.**

Сообщения об ошибках нормализации называют отсутствующее поле, а не значение (`payload.pid отсутствует`). Это сделано намеренно: значение в тексте ошибки обошло бы и настройки сбора, и редакцию, потому что лог не подчиняется ни тому, ни другому.

## Что не защищено

- **База не шифруется.** Кто получил доступ к файлу БД — получил историю процессов целиком.
- **У API нет аутентификации.** Любой процесс того же пользователя может прочитать историю через loopback. Это осознанное состояние версии: локальный общий секрет между Agent и Core запланирован в §33 позже, а не забыт.
- **Разграничения прав нет.** Agent работает без повышения прав (§67) и потому не может прочитать путь и командную строку процессов других пользователей, даже если флаги включены. Это ограничение, а не ошибка: §67 запрещает запускать весь продукт от администратора ради одного коллектора.
- **Automatic retention отсутствует.** База растёт, пока её не удалят (§39). Политики хранения — будущая работа, и архитектура ей не мешает: сырые и нормализованные события лежат в разных таблицах.
- **Логи не редактурируются.** Они не содержат payload, но содержат идентификаторы и пути — например, путь к базе при старте Core.

## Как проверить самому

Убедиться, что слушает только loopback:

```powershell
curl http://127.0.0.1:7342/api/v1/health
```

Попытка поставить `host = "0.0.0.0"` в конфигурации завершается ошибкой при загрузке настроек, а не предупреждением в логе.

Увидеть, что **действительно** сохранено — то есть свои данные, а не описание настроек:

```powershell
cd core
uv run chronoscope events --limit 20
uv run chronoscope event <id>        # видно состав атрибутов целиком
```

Посмотреть, что уходит в Core, можно на самом Agent: его конфигурация и флаги сбора печатаются при старте в `agent_started`.

Ограничить сбор: `capture_path`, `capture_command_line` и `capture_user` в `false` — это значения по умолчанию, то есть «ничего не делать» уже достаточно. Дополнительно можно задать `redact_command_line_patterns`, если командную строку всё же собирают.

Удалить историю: остановить Core, затем

```powershell
pwsh scripts/reset-dev-data.ps1
```

Скрипт удаляет содержимое `data/`, не трогая исходный код, миграции, фикстуры и конфигурацию. Если база лежит в другом месте — удалить файл БД по пути `[storage] database_path` вместе с файлами `-wal` и `-shm`. Пока Core запущен, файл на Windows может не удалиться: он держит базу открытой.

## Связь с уровнями §37

| Уровень | Что это значит в 0.0.2 |
|---|---|
| Minimal | состояние по умолчанию: имя, PID, связь с родителем, времена |
| Standard | включение `capture_path`, `capture_user` и `capture_command_line` — каждое поле отдельным флагом |
| Extended | будущие детальные коллекторы (§8.3); в 0.0.2 их нет |

Отдельного ADR о приватности пока нет: модель описана в §37–§38 спеки, здесь и в [`SECURITY.md`](../SECURITY.md). Изменение самой модели приватности требует ADR, а не правки одного документа (см. [CONTRIBUTING.md](../CONTRIBUTING.md)).

## Что запланировано

Только то, что уже названо в спеке, и ничего сверх:

- §38 — privacy filter как отдельный шаг pipeline между сбором и `RawEvent`;
- §39 — политики хранения и ограничение роста базы;
- §33 — общий секрет между Agent и Core.

Считать это обещанием не стоит: пока перечисленного нет, действует описанное выше состояние.
