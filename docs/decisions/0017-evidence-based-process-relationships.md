# ADR-0017: Связи процессов как ограниченное представление свидетельств

## Статус

Принято, 2026-10-10. Реализация и проверка — §77.3.

## Аудит 0.0.4

База аудита — `d3b73715331e4c6bbfdcb7104659134c49a0f056`, проверена через
`git fetch origin`. Таблиц процессов нет. ProcessNormalizer записывает
`parent_pid` и найденный `actor` при ingest. Старый lookup выбирает последний
`process.started` по boot/PID до старта ребёнка, но не проверяет host, exit и
конкурирующие свидетельства. ProcessDetail выбирает первого подходящего actor
и скрывает конфликт parent PID. Поэтому historical actor — свидетельство
решения старого нормализатора, а не независимое доказательство родительства.

Имеются индексы `(timestamp,id)`, `(type,timestamp,id)`,
`(actor_id,timestamp,id)`, `(subject_id,timestamp,id)`; PID находится в JSON.
Пагинация событий — курсор `(timestamp,id)` DESC, без OFFSET. UI сохраняет
страницы списка, но помнит только одно исходное событие, а переход к событиям
процесса меняет фильтры списка. Слои проверяются AST-тестами; API не пишет SQL.

## Решение и design review API

1. Связь `parent_of` вычисляется при чтении immutable Events; новой таблицы,
   materialization, графовой БД и confidence score нет.
2. `resolved` означает единственного согласованного кандидата среди доступных
   наблюдений, **не доказанную причинность** и не гарантию полноты WMI.
   Отсутствующий exit не доказывает, что процесс работал в момент старта ребёнка.
3. Проверяются host, известный boot, PID, время старта, все известные exits,
   parent PID и сохранённые process actors. Parent start <= child start;
   exit < child start исключает кандидата. Несколько допустимых кандидатов —
   `unresolved/ambiguous_candidates`, отсутствие — `insufficient_observation`.
   Несогласованные identity/timestamps/PID/actors — `conflicting`.
   Actor не разрешает неоднозначность самостоятельно. Ссылка без наблюдений
   не становится фиктивным узлом. События завершения могут дать время старта.
4. Все lifecycle-события экземпляра проверяются вместе, включая поздние.
   Если ограничение чтения мешает проверить кандидатов, связь не разрешается.
   Следующий запрос может изменить view; исходные события остаются прежними.
5. Два новых GET: `/api/v1/processes/{id}/relations?limit=100` (1..200),
   `/api/v1/processes/{id}/tree?depth=3&max_nodes=200` (depth 0..5, nodes 1..200).
   Дерево — плоский список узлов с parent ID/depth, без рекурсивного JSON.
   В ответах `truncated`, `reasons`, `observation_complete=false`.
   Неизвестный id — 404, некорректный id/параметр — 422; конфликт — данные 200.
6. Related events: дополнительный `/events?entity_id=proc_...`, означающий
   `actor_id OR subject_id`. Порядок, курсор, время и остальные фильтры общие.
   Отдельный `/related-events` дублировал бы существующий контракт. Записанные
   actor references остаются entity references, даже если Connect их оспаривает.
   `system.event` по соседству не входит в эту выборку. Temporal context вне scope.
7. Новые relations/tree читаются в одной явной SQLite read transaction.
   Между отдельными HTTP-запросами snapshot consistency не обещается.
8. Batch-запросы по уровням, кэш наблюдений на запрос, visited set; лимит
   чтения 10000 строк за запрос и не более 2000 найденных детей за уровень.
   При исчерпании бюджета явно сообщается `evidence_limit`. Лимит доказательств
   может дать меньше узлов, чем max_nodes. Порядок детей — start, instance ID.
9. ProcessDetail сохраняет форму контракта; локальные противоречия parent PID
   и actor больше не скрываются. Актуальная проверенная связь принадлежит
   `/relations`; UI/CLI Connect показывают её отдельно от исторических ссылок.

## Альтернативы и последствия

Только actor-index пропускает поздно найденных родителей. Только PID создаёт
ложные связи. «Последний старт победил» скрывает конкурирующие наблюдения.
Чтение всей boot session без лимита и запрос на каждый узел не подходят.
Scoped expression indexes по PID и parent PID допустимы после измерения
реальных SQL/query plans; они требуют миграции, но не меняют Events.

Цена консервативности — часть правдоподобных связей останется неизвестной.
Безопасный отказ при лимите предпочтительнее выбора по неполной выборке.
WMI, disk spool, новые collectors и Timeline здесь не изменяются.

## Измерение индексов

`scripts/benchmark-connect.py`, 2026-10-10: 1000 и 20000 детерминированных Events,
первая выборка с новым соединением и семь повторов; OS cache не сбрасывался.
На 20000 events медиана relations 37.11 → 1.54 мс, tree chain 88.44 → 3.34 мс,
wide tree (200 узлов) 45.84 → 15.85 мс. Соответственно 5/11/4 SELECT, независимо
от числа узлов внутри уровня. Bulk insert 260 → 325 мс (один замер, не ingest SLA).
До: `ix_events_type_timestamp (type=?)` + временное DISTINCT дерево;
после: `ix_events_process_pid/parent_pid (host_id=?, boot_id=?, <expr>=?)`.
Поэтому миграция 0003 добавляет ровно два scoped expression index. Цена — место
и обслуживание при insert. Entity-events использует существующие actor/subject
индексы и SQL UNION двух потоков, каждый ограничен page limit+1; временная
сортировка объединяет максимум 2002 строки, а не всю историю процесса.
