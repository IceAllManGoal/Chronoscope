# ADR-0005: Сохранять raw events до нормализации

## Статус

Принято. Дата: 2026-09-18

## Контекст

Нормализация неизбежно является интерпретацией: она решает, что в источнике было `process.started`, какие поля важны, как вычислить идентичность сущности. Интерпретация опирается на текущее понимание и содержит ошибки.

Если хранить только нормализованные события, то ошибка нормализатора означает безвозвратную потерю информации: восстановить её можно только новым сбором, то есть ожиданием, пока проблема воспроизведётся. Это особенно болезненно, потому что Chronoscope ценен именно историей, а интересные события обычно уже произошли.

## Решение

**Raw event сохраняется до нормализации** (§11).

```text
Source → Collector → RawEvent → Ingest → Raw Store
                                              ↓
                                          Normalizer
                                              ↓
                                          Event Store
```

Оба уровня хранятся: `raw_events` и `events` (§26). `RawEvent` содержит source-specific payload в форме, максимально близкой к источнику, и не «обогащается» догадками.

Следствия, зафиксированные явно:

- если нормализатор не понимает payload, raw event **всё равно сохраняется**, а неудача логируется (§60). Данные не уничтожаются;
- сохранённый raw event позволяет прогнать новую версию нормализатора по уже собранной истории;
- `Event.raw_event_id` связывает нормализованное событие с источником, благодаря чему результат нормализации всегда проверяем.

## Последствия

**Положительные:**

- **reprocessing:** смена схемы или исправление bug в парсере не требует повторного сбора;
- **debugging:** видно, что именно прислал источник, а не только то, что из этого получилось;
- **миграция normalizers:** старые данные можно переработать новым кодом;
- **разработка аналитики на исторических данных** без ожидания новых событий;
- **устойчивость:** ошибка интерпретации перестаёт быть потерей данных и становится исправимым дефектом.

**Отрицательные и принятые издержки:**

- **двукратный расход диска** на каждое событие — самая существенная цена решения;
- raw storage растёт быстрее нормализованного, и именно ему в первую очередь нужна отдельная retention-политика (§29, §39). Политики в 0.0.1 нет;
- ingest становится дороже: запись raw event добавляется к записи нормализованного;
- появляется соблазн считать raw-слой «источником истины» для запросов. Нет: запросы идут по `events`, а raw-слой — для переобработки и диагностики;
- при удалении raw-данных по retention связь `Event → RawEvent` станет висячей. Это нужно учесть при проектировании retention: либо `raw_event_id` становится nullable при удалении, либо raw-данные агрегируются перед удалением.
