# ADR-0008: Modular monolith, без микросервисов

## Статус

Принято. Дата: 2026-09-18

## Контекст

Chronoscope собирает события, нормализует их, хранит, а в будущем будет коррелировать, анализировать и строить отчёты. Соблазн разнести эти обязанности по отдельным сервисам велик: «collector service», «normalization service», «analytics service», «query service» — с брокером сообщений между ними.

Для локального продукта это означало бы Kafka, Redis или RabbitMQ, Kubernetes и service mesh на компьютере пользователя. Стоимость сопровождения такого стека заведомо превышает любую выгоду: Chronoscope — один локальный продукт, а не распределённая платформа (§54).

## Решение

Основной подход:

> **Modular monolith + отдельный platform agent.**

Core — один процесс с чёткими внутренними границами между слоями (§50):

```text
api/              HTTP
application/      use cases
domain/           модель предметной области
normalization/    raw → Event
infrastructure/   SQLite, конфигурация, логирование
analytics/        будущая аналитика
```

Границы обеспечиваются правилами зависимостей и ревью, а не сетевыми вызовами. Agent остаётся отдельным компонентом, но по причине платформенной изоляции ([ADR-0002](0002-agent-core-separation.md)), а не ради «сервисной архитектуры».

В 0.0.1 не используются: Kafka, Redis, RabbitMQ, Kubernetes, service mesh, PostgreSQL, ClickHouse (§54, §74).

## Последствия

**Положительные:**

- запуск продукта — одна команда, без инфраструктуры;
- отладка не требует распределённой трассировки: весь путь события виден в одном процессе;
- транзакция между записью raw event и нормализованного события возможна без распределённых протоколов;
- нет накладных расходов на сериализацию между внутренними компонентами;
- installer, когда появится, будет установкой приложения, а не развёртыванием кластера.

**Отрицательные и принятые издержки:**

- границы слоёв поддерживаются дисциплиной: компилятор не помешает `api/` напрямую обратиться к SQLAlchemy. Смягчение — явные правила в §50 и [`ARCHITECTURE.md`](../ARCHITECTURE.md), проверяемые на ревью;
- масштабирование Core возможно только вертикальное. Для локального продукта это не ограничение, но для будущего multi-host сценария — ограничение;
- один процесс означает и общий отказ: падение Core останавливает и ingest, и запросы. Смягчение — Agent буферизует события и переживает недоступность Core (§34, §62);
- если когда-либо возникнет реальная необходимость разделить Core, рефакторинг будет стоить дорого. Решение сознательно принимается как преждевременно не оплачиваемое: разделение делается тогда, когда для него есть измеренная причина, а не заранее (§54).
