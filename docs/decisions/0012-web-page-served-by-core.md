# ADR-0012: Страница отдаётся Core, и в 0.0.2 у неё нет сборки

## Статус

Принято. Дата: 2026-09-20

## Контекст

§77 открывает версию 0.0.2 пунктом «базовая local web page». §55 заранее зафиксировал стек для будущего UI — TypeScript, React, Vite — и обосновал его сложными задачами интерфейса: виртуализированный timeline, графики, граф процессов. Там же §55 сознательно отложил решение о том, чем UI отдаётся (локальный web UI, WebView2 или иной shell), «до появления работающего интерфейса». Интерфейс появляется, и решение нужно принимать.

Три обстоятельства делают выбор неочевидным.

1. **У базовой страницы нет ни одной из задач, ради которых выбирался React.** §77 просит список событий с пагинацией, фильтрами и деталями одного события. Это таблица и панель подробностей — ни виртуализации, ни графиков, ни графа.
2. **React и Vite — это второй toolchain.** Node нужен и разработчику, и CI; появляется шаг сборки, а его результат — генерируемые файлы, которые либо попадают в git, либо требуют сборки перед первым запуском.
3. **Инвариант 10 §81 требует, чтобы UI не читал SQLite напрямую.** Значит страница в любом варианте — клиент API Core, и это не зависит от выбора.

## Решение

**Страница отдаётся самим Core** как статика из его пакета, по пути `/ui`, и в 0.0.2 **не имеет шага сборки**: это обычные HTML, CSS и JavaScript в `core/chronoscope/web/`.

Почему отдаёт Core:

- **один процесс вместо двух.** Чтобы увидеть историю, достаточно запустить Core и открыть адрес, который он печатает при старте;
- **один origin.** Страница и API живут на одном loopback-адресе, поэтому CORS, прокси и вопросы аутентификации между ними не возникают вовсе. Отдельный сервер потребовал бы их решать ради базовой страницы;
- **статика внутри пакета находится всегда** — независимо от того, откуда запущен Core и как он установлен.

Почему без сборки:

- §70 запрещает строить инфраструктуру заранее, а §65 — добавлять зависимости ради небольшого удобства. Сборка здесь означала бы второй toolchain (Node, npm, конфигурация Vite, шаг в CI) ради страницы, которой не нужны возможности, ради которых этот toolchain выбирался;
- то, что отдаётся, — исходники, а не генерируемые файлы, и в git не попадает ничего собираемого;
- страница работает сразу после клонирования, без `npm install`.

`frontend/` сохраняется как зарезервированное место для UI на React/Vite (§55): он появится, когда интерфейсу действительно понадобятся виртуализация и графы, то есть около 0.1.0 «Timeline». Тогда этот ADR подлежит пересмотру.

## Последствия

**Положительные:**

- запуск «посмотреть историю» — одна команда, без Node;
- нет CORS и прокси: страница и API на одном origin;
- нет генерируемых файлов в репозитории и второго toolchain в CI;
- Core остаётся единственным владельцем базы, инвариант 10 соблюдён по построению.

**Отрицательные и принятые издержки:**

- **Core начинает отдавать UI.** §9.1 перечисляет приём, нормализацию, хранение и API, но не раздачу статики, так что роль Core расширяется и в дереве появляется `web/`. Смягчение: статика монтируется по отдельному пути `/ui` и на API не влияет.
- **Страница будет переписана.** Когда появится виртуализированный timeline, её заменят на React/Vite, и код не переиспользуется — переиспользуются только вызовы API. Цена принята сознательно: страница нужна сейчас, а её переписывание дешевле, чем преждевременная инфраструктура.
- **Нет HMR и типизации.** Разметку и логику можно править только перезагрузкой, а опечатки в JavaScript не ловит компилятор. Смягчение: в CI добавляется `node --check` — синтаксическая проверка, не требующая ни сборки, ни установки пакетов.
- **Нет автоматических тестов поведения страницы.** Браузерной автоматизации в проекте нет, поэтому проверяется то, что Core отдаёт файлы, а вызовы API покрыты тестами API; логика страницы проверяется вручную. Ограничение записано, а не замаскировано: считать страницу покрытой тестами было бы неправдой.
- **`/ui`, а не `/`.** Адрес печатается в логе при старте Core, и корень `/` перенаправляет туда же — иначе открытие единственного известного адреса давало бы 404.

## Когда пересмотреть

- Появится необходимость в виртуализации, графиках или графе процессов (0.1.0 «Timeline») — тогда вернуться к стеку §55 и, вероятно, к вопросу о desktop-обёртке.
- Появится требование отдавать UI отдельно от Core — тогда придётся решать CORS и способ запуска второго процесса.
