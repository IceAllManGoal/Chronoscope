# ADR-0003: Единая модель событий

## Статус

Принято. Дата: 2026-09-18

## Контекст

Источники данных о работе компьютера несовместимы между собой: список процессов, Windows Event Log, ETW, сетевые соединения, DNS, реестр, файловая система, драйверы, службы, Windows Update, crash reports. У каждого своя структура, свои идентификаторы, своя гранулярность и своё представление времени.

Можно было бы хранить данные каждого источника в своей таблице и строить UI поверх них по отдельности. Это дешевле на старте, но делает невозможным главное обещание продукта: ответить на вопрос «что происходило в 21:43», когда ответ складывается из событий *разных* источников, и построить связи между ними.

## Решение

Все источники приводятся к **одной** модели событий. Центральные сущности:

```text
RawEvent    универсальная оболочка вокруг source-specific payload (§12)
Event       нормализованное событие — центральная сущность Chronoscope (§13)
```

Внутреннее ядро строится вокруг события, а не вокруг процесса, Windows или конкретного API (§6.3). `Event` не зависит от того, из какого источника он получен: источник фиксируется полем `source`, а специфика источника остаётся в `attributes`.

События связывают сущности через `actor` и `subject` (§20). Добавление нового источника не меняет модель — оно добавляет нормализатор, который порождает события уже существующих или новых типов.

## Последствия

**Положительные:**

- временная шкала становится единой: события разных источников сортируются и фильтруются одинаково;
- correlation и analytics работают поверх одной структуры, а не поверх N разных (§22);
- UI пишет один timeline, а не N специализированных экранов (§41);
- новые collectors добавляются без изменения ядра (технический критерий §79).

**Отрицательные и принятые издержки:**

- нормализация неизбежно теряет часть source-specific деталей. Компенсация — обязательное сохранение `RawEvent` до нормализации ([ADR-0005](0005-preserve-raw-events.md));
- модель должна быть достаточно общей, чтобы вместить источники, которых ещё нет. Это давление в сторону преждевременной абстракции, и ему нужно сопротивляться (§80): абстракции добавляются там, где уже есть реальная граница;
- часть полей уходит в `attributes` как JSON, что ухудшает строгость схемы и усложняет запросы. Денормализация возможна позже, когда появятся стабильные query patterns (§28);
- единая модель создаёт соблазн «сложить в неё всё», что ведёт к scope explosion (§80). Фильтр остаётся прежним: помогает ли это понять историю системы во времени.
