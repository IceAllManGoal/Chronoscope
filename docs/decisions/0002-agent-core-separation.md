# ADR-0002: Разделить Agent и Core

## Статус

Принято. Дата: 2026-09-18

## Контекст

Chronoscope должен собирать данные из операционной системы и хранить их в единой модели. Напрашивается единый процесс, который и собирает, и хранит, и отдаёт API: меньше движущихся частей, проще запуск.

Против этого есть четыре обстоятельства (§10):

1. **Платформа.** Сбор данных глубоко платформенный (Windows API, Event Log, ETW, процессы), а хранение, API и аналитика — нет.
2. **Права.** Некоторым коллекторам понадобятся elevated privileges. Запускать весь продукт от администратора «потому что одному коллектору когда-нибудь понадобятся права» — прямой путь к раздутой поверхности атаки (§67).
3. **Профиль нагрузки.** Agent оптимизируется под стабильный непрерывный сбор, Core — под хранение, запросы и аналитику. Это разные требования к памяти, конкурентности и времени отклика.
4. **Воспроизводимость.** Если сбор и разбор разделены, сохранённые raw-данные можно переобработать новой версией Core без повторного сбора (§29).

## Решение

Два отдельных runtime-компонента с явной границей между ними:

```text
Chronoscope Agent    Windows-native, C#/.NET
                     запускает коллекторы, формирует RawEvent, буферизует, доставляет

Chronoscope Core     Python, FastAPI
                     принимает, валидирует, нормализует, хранит, отдаёт API
```

Agent знает про Windows и не знает про Chronoscope как продукт. Core знает про Chronoscope и не знает про Windows.

Agent **не должен**: выполнять долгую аналитику, строить граф событий, принимать продуктовые решения, работать с основной БД напрямую, содержать UI, знать внутреннюю структуру аналитических модулей (§8.1).

Граница между компонентами — HTTP по loopback и общий формальный контракт в `shared/schemas/`. Никакого общего кода, никаких общих сборок.

## Последствия

**Положительные:**

- добавление `Chronoscope.Agent.Linux` или `.MacOS` не потребует переписывать Core;
- Core не зависит от Windows API (инвариант §81);
- права Agent и Core независимы: Core не требует elevated privileges;
- raw-данные можно переобработать без повторного сбора;
- сбой коллектора не роняет хранилище, а сбой Core не останавливает сбор мгновенно (in-memory buffer, §34).

**Отрицательные и принятые издержки:**

- два процесса нужно запускать, останавливать и диагностировать вместо одного;
- появляется транспортный слой и всё, что с ним связано: сериализация, батчи, retry, идемпотентность, backpressure (§34);
- контракт требует версионирования и контрактных тестов (§52, §58);
- состояние системы распределено: «почему нет событий» может означать проблему в Agent, в транспорте или в Core, и диагностика обязана это различать (§35, §60);
- локальный запуск в dev-режиме требует двух терминалов (§63).
