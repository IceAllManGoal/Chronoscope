# ADR-0011: Три проекта Agent и явная платформенная цель сборки

## Статус

Принято. Дата: 2026-09-20

## Контекст

[ADR-0002](0002-agent-core-separation.md) зафиксировал единственную несущую границу Agent — платформенную, и `docs/ARCHITECTURE.md` §5 на этом основании сократил раскладку §48 спеки с четырёх проектов (`Agent`, `Abstractions`, `Transport`, `Collectors.Windows`) до двух:

```text
Chronoscope.Agent                     платформенно-нейтральный
Chronoscope.Agent.Collectors.Windows  платформенно-зависимый
```

Это была осознанная борьба с преждевременной абстракцией (§70, §80): при одном коллекторе и одном транспорте выделять под каждый отдельный проект не за что. Композиционный корень — точка, где конкретный коллектор соединяется с транспортом, — в этом решении не рассматривался.

При реализации он оказался решающим. Композиционный корень обязан знать **и** платформенно-нейтральные части, **и** платформенного коллектора. Платформенный коллектор обязан ссылаться на нейтральные абстракции (`IProcessObservationSource`, `IBootSessionProvider`, `ProcessCollectorSettings`), чтобы их реализовывать. Если точка входа живёт в нейтральном проекте, ссылка получается встречной, и два проекта такой конфигурацией просто не собираются.

Тем же прогоном обнаружилась вторая проблема. Оба проекта были нацелены на `net8.0`, то есть объявлены кроссплатформенными, хотя один из них вызывает WMI. Анализатор платформенной совместимости (CA1416) выдал 15 предупреждений — это и был сигнал, что объявленная платформа не соответствует фактической.

## Решение

**Три проекта вместо двух.** Композиционный корень получает собственный исполняемый проект:

```text
src/Chronoscope.Agent/                     net8.0          библиотека: контракт, идентичность,
                                                           конфигурация, транспорт, абстракции
src/Chronoscope.Agent.Collectors.Windows/  net8.0-windows  библиотека: WMI, платформенные порты
src/Chronoscope.Agent.Host/                net8.0-windows  исполняемый: композиционный корень
tests/Chronoscope.Agent.Tests/             net8.0-windows  тесты
```

**Платформа объявляется явно.** Всё, что вызывает Windows API, нацелено на `net8.0-windows`; нейтральное ядро остаётся на `net8.0`.

Направление ссылок:

```text
Host ──► Agent (ядро)
  └───► Collectors.Windows ──► Agent (ядро)
```

## Последствия

**Положительные:**

- **Платформенная изоляция стала проверяемой компилятором, а не дисциплиной.** Проект на `net8.0` физически не может сослаться на проект `net8.0-windows`, поэтому обратиться к Windows API из ядра невозможно — это ошибка сборки, а не замечание на ревью. Для Core ту же роль играет тест правил слоёв §50; здесь ограничение сильнее, потому что его накладывает сам инструмент.
- Композиционный корень получил имя и место. Он перестал быть «кодом, который непонятно к какому проекту относится».
- `Chronoscope.Agent.Host` — единственное место, знающее обо всех частях сразу, поэтому зависимость от платформы локализована в нём одном и видна по имени проекта.
- Появление второго Agent'а (`Chronoscope.Agent.Linux` или `.MacOS`) сводится к третьему проекту-хосту; ядро и его тесты не меняются вовсе.

**Отрицательные и принятые издержки:**

- **Раскладка расходится с `ARCHITECTURE.md` §5 и §48 спеки.** Оба документа придётся обновить, и это не косметика: §76 требует, чтобы спека соответствовала реальной архитектуре, а расхождение в дереве каталогов читается как ошибка того, кто её откроет.
- **Проектов стало больше, чем нужно для одного коллектора.** Возражение ADR-0002 остаётся в силе: будь точка входа частью нейтрального проекта, хватило бы двух. Цена принята сознательно — альтернативой было бы либо отдать исполняемый проект платформенному коллектору (имя `Collectors.Windows` как хоста вводит в заблуждение), либо загружать коллектор рефлексией, то есть строить плагинную инфраструктуру ради одного плагина (§70).
- **`dotnet run` теперь указывает на `Chronoscope.Agent.Host`,** а не на `Chronoscope.Agent`. Команды в документации и в `README.md` должны это учитывать; расхождение обнаружится сразу, но только если документация обновлена не будет.
- **Целевая платформа `net8.0-windows` привязывает Agent к Windows,** что для 0.0.1 и так верно (ADR-0006), но означает, что тесты Agent не запустятся на Linux-раннере. CI обязан использовать Windows-раннеры — как и предписывает ADR-0006.
- **Хост стал Windows-проектом, хотя логика в нём платформенно-нейтральна.** Это следствие ссылки на платформенного коллектора: проект с такой ссылкой обязан быть платформенным. Если однажды таких ссылок станет несколько под разные платформы, понадобится либо хост на каждую платформу, либо плагинная загрузка — тогда это решение стоит пересмотреть.

## Когда пересмотреть

- Появится второй платформенный Agent — тогда проверить, что ядро действительно осталось нейтральным, а различие свелось к проекту-хосту.
- Появится второй коллектор для той же платформы — тогда вернуться к вопросу о `Abstractions`/`Transport` как отдельным проектам (§48), поскольку граница станет не только платформенной.
- Появится CI на Linux-раннерах для ядра — тогда вынести тесты нейтральных частей в проект на `net8.0`, чтобы они там исполнялись.
