# ADR-0004: SQLite как основная БД в 0.x

## Статус

Принято. Дата: 2026-09-18

## Контекст

Chronoscope — local-first продукт (§6.1): данные пользователя находятся на его компьютере, работа не требует аккаунта, сервера и интернет-соединения. Хранить нужно растущий поток структурированных событий с запросами по времени и сущностям.

Рассматривались: SQLite, PostgreSQL, ClickHouse, встраиваемые аналитические решения и файловые форматы (JSON Lines, Parquet).

PostgreSQL и ClickHouse требуют отдельного серверного процесса. Это означает installer, конфигурацию, credentials, порты, backup и диагностику «почему не поднялась БД» — для локального инструмента это цена без соответствующей выгоды (§25). ClickHouse вдобавок подразумевает объёмы, которых в 0.x нет. Файловые форматы без индексов не дают нужных запросов по времени и сущностям.

## Решение

Основная БД версии 0.x — **SQLite**, один локальный файл.

Исходные настройки, подлежащие подтверждению benchmark'ами (§25):

```text
WAL mode
foreign_keys = ON
synchronous = NORMAL
busy_timeout configured
```

Доступ к БД — только через слой репозиториев. Схема изменяется только через Alembic-миграции (§81, инвариант 11).

## Последствия

**Положительные:**

- zero configuration: нет серверного процесса, нет credentials, нет портов;
- один файл — тривиальны backup, перенос и удаление данных пользователем;
- транзакции, индексы и JSON-функции доступны;
- воспроизводимые тесты: временная БД создаётся и уничтожается в рамках теста (§58);
- `data/` можно целиком исключить из git, что и сделано.

**Отрицательные и принятые издержки:**

- **конкурентная запись ограничена.** SQLite допускает одного писателя в момент времени. При росте нагрузки ingest это станет узким местом. Смягчение: батчевые вставки, WAL, короткие транзакции, измерение метрик (§61);
- **аналитические запросы по большой истории медленнее,** чем в колоночных СУБД. Ожидаемое решение — cold storage на Parquet с DuckDB (§30), но это явно вне 0.0.1;
- рост файла требует retention-политик (§39), которых пока нет;
- переход на другую СУБД в будущем потребует работы. Смягчение — изоляция за репозиториями и миграции: смена хранилища не должна затрагивать `domain/` и use cases;
- настройки из списка выше нужно подтвердить измерениями, а не принимать на веру.
