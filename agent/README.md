# Chronoscope Agent

Компонент, который наблюдает за Windows и доставляет сырые события в Core.

Полное описание проекта, архитектуры и модели событий — в корне репозитория:

- [`../docs/PROJECT_SPEC.md`](../docs/PROJECT_SPEC.md) — главный документ проекта;
- [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) — компоненты, слои, поток данных;
- [`../docs/EVENT_MODEL.md`](../docs/EVENT_MODEL.md) — модель `RawEvent` и `Event`;
- [ADR-0011](../docs/decisions/0011-agent-project-structure.md) — почему проектов три.

## Требования

```text
Windows
.NET SDK 8+
```

## Запуск

Как и в §63, это два процесса в двух терминалах:

```powershell
# Терминал 1: Core
cd core
uv sync --all-groups
uv run alembic upgrade head
uv run python -m chronoscope

# Терминал 2: Agent
dotnet run --project agent/src/Chronoscope.Agent.Host
```

Точка входа — `Chronoscope.Agent.Host`, а не `Chronoscope.Agent`: композиционный
корень обязан знать и нейтральное ядро, и платформенного коллектора, поэтому он
вынесен в отдельный проект (см. ADR-0011).

Проверить, что события дошли:

```powershell
curl "http://127.0.0.1:7342/api/v1/events?type=process.started"
```

│   │   ├── Identity/                          ULID (§17), host_id (§15), boot_id (§16)
│   │   ├── Logging/                           структурированные JSON-логи (§35)
│   │   └── Transport/                         ограниченный буфер и отправка пакетами (§34)

Платформенная граница здесь не декларация, а ограничение компилятора: проект на
`net8.0` не может сослаться на проект `net8.0-windows`, поэтому Windows API из
ядра недостижим в принципе.

## Конфигурация

Тот же файл, что и у Core: §36 предполагает один файл на весь проект. Путь —
переменная окружения `CHRONOSCOPE_CONFIG`, иначе `chronoscope.toml` в текущем
каталоге. Адрес Core берётся из секции `[core]`, а не из отдельного ключа: два
независимых описания одного адреса разошлись бы.

```toml
[core]
host = "127.0.0.1"          # только loopback: см. ниже
port = 7342

[agent]
batch_size = 50             # событий в пакете
flush_interval_ms = 500     # как долго ждать накопления пакета
buffer_capacity = 10000     # ёмкость ограниченной очереди (§34)
request_timeout_ms = 10000
data_directory = ""         # по умолчанию %LOCALAPPDATA%\Chronoscope

[collectors.process]
enabled = true
capture_path = false
capture_command_line = false
capture_user = false

[privacy]
redact_command_line_patterns = []
```

Секции другого компонента (`[storage]`) пропускаются, а **неизвестные ключи
внутри своих секций отвергаются**: иначе опечатка в имени параметра выглядела бы
как «настройка не применилась».

**Адрес Core проверяется на loopback.** Небезопасная конфигурация невозможна: если
бы Agent мог отправлять события на внешний адрес, собранные сведения о работе
компьютера уходили бы за пределы машины (§33, ADR-0007).

## Приватность

По умолчанию собирается уровень **Minimal** — имя процесса, PID, связь с
родителем и времена; путь, командная строка и SID пользователя не собираются.
Поля контракта необязательные, поэтому «выключено» означает **отсутствие поля**,
а не пустое значение: пустое выглядело бы как «источник не сообщил», и отличить
«не собирали» от «не удалось получить» стало бы невозможно.

Расхождение, которое стоит знать: §36 показывает в примере
`capture_command_line = true`, тогда как §37 относит командную строку к уровню
Standard и предупреждает, что она может содержать токены, пароли и приватные
пути. Выбран более осторожный вариант — §6.2 объявляет privacy by default.
Решение о значении по умолчанию остаётся за мейнтейнером.

Ключ `capture_path` в примере §36 отсутствует, но §37 относит путь к уровню
Standard, а Minimal ограничивает набор полями «name, pid, parent relation,
timestamps»: без отдельного флага уровень Minimal был бы недостижим.

Шаблоны `redact_command_line_patterns` вырезают совпадения из командной строки
(§38). По умолчанию командная строка не собирается вовсе, поэтому шаблоны нужны
тем, кто собирать её всё же решил.

Полная модель приватности — что собирается, где лежит и что остаётся
незащищённым — в [`docs/PRIVACY.md`](../docs/PRIVACY.md).

## Наблюдение за процессами

Коллектор использует собственные события WMI (`__InstanceCreationEvent` и
`__InstanceDeletionEvent` по `Win32_Process`). Трассировочные классы
(`Win32_ProcessStartTrace`) полнее, но требуют повышенных прав, а §67 запрещает
запускать весь продукт от администратора из-за одного коллектора; §8.4 для
первой итерации прямо допускает более простой механизм. Цель 0.0.1 — проверить
pipeline, а не собрать максимум данных.

**Измеренная полнота.** Полнота наблюдения проверена управляемым экспериментом:
запускается известное число процессов, и проверяется, сколько из них попало в
события по PID.

| Процессы | Запущено | Увиден старт | Увиден выход |
|---|---|---|---|
| `cmd.exe` | 5 | 5 | 5 |
| `notepad.exe` | 5 | 4 | 4 |

Потерь буфера при этом не было (`event_dropped` в логах отсутствует), то есть
потеря происходит на этапе наблюдения. Причина — `WITHIN 1`: WMI сравнивает
снимки класса раз в секунду, поэтому процессы, живущие меньше интервала опроса,
могут не попасть ни в один снимок. Разброс между прогонами большой.

**Следствие, которое нельзя забывать:** §75 требует увидеть запуск и завершение
`notepad.exe`, и это выполняется, но **не гарантируется**. Для системы, весь смысл
которой — доверять истории, полнота наблюдения обязана стать гарантией.
Направление решения: трассировочные классы WMI или ETW (§8 относит ETW на
следующие версии). Выбор стоит делать по измерению, а не по предположению — этот
раздел и есть заготовка такого измерения.

**Измерено в 0.0.3: у приложений из Microsoft Store родитель не наблюдаем.**
Запуск `notepad.exe` на Windows 11 порождает **два** процесса:

- псевдоним исполнения — его родитель запустившая оболочка, и связь
  устанавливается;
- процесс приложения `Notepad.exe` — его создаёт посредник активации, который
  живёт меньше интервала опроса и в историю не попадает.

Поэтому у процесса приложения `parent_resolved: false`, а `parent_pid` указывает на
процесс, которого в истории нет. Измерено на одном прогоне, четыре экземпляра
`Notepad.exe`: связь установлена у одного (псевдоним), у трёх процессов приложения —
нет. Для процессов, которые оболочка запускает напрямую, связь устанавливается
полностью: измеренная цепочка `powershell → cmd.exe → ping.exe` разрешилась на всех
трёх уровнях.

Это не ошибка разрешения: Core честно помечает связь как неустановленную, потому
что родителя в истории не было. Но знать об этом нужно — «кто запустил» для
приложений Store по истории не восстанавливается, пока коллектор не станет полнее.

## Тесты

```powershell
cd agent
dotnet test Chronoscope.Agent.sln
```

Проверяются части, которые не видны при обычном запуске: ULID сверивается с
реализацией Core на конкретных значениях (эталоны получены выполнением
`chronoscope.domain.ulid_from`), форма JSON сверяется со
`shared/schemas/raw-event.schema.json`, а также поведение при переполнении
буфера, при недоступном Core и при завершении.

Отдельно проверяется, что тест способен упасть: у проверки правил слоёв есть
страховка от вырожденного прохода, и при разработке она уже срабатывала.

## Известные ограничения

- **Полнота наблюдения не гарантирована** (см. выше) — главное ограничение.
- **У приложений из Microsoft Store родитель процесса приложения не наблюдаем** (см. выше): Core помечает связь как неустановленную, а не выдумывает её.
- Завершение по `Ctrl+C` отправляет накопленное, но покрыто только юнит-тестом:
  вживую проверялось принудительное завершение процесса.
- Повышение прав не требуется; при работе без прав `ExecutablePath` и
  `CommandLine` для процессов других пользователей недоступны — это нормальное
  состояние конфигурации, а не ошибка, поскольку поля необязательные.
- `exit_code` не приходит: собственное событие удаления процесса его не сообщает.
